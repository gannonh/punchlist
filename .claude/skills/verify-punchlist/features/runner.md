# Runners, claims and runs

`pl runner start` registers a runner with the server, sends a heartbeat every 10 seconds, and long-polls `POST /api/runs/claim`. When a person moves an issue to Start, the server moves it to In Progress as the runner's actor, creates a run and its first attempt under a 30-second lease, and returns the claim. The runner adds a worktree on `feature/<id>` (no word of the title) from the repository's default branch, starts `claude -p` with the issue inside a fence, streams the agent's output to the run log, and reports the outcome with its duration and tokens. `pl issue show` lists the issue's runs with the last 20 log lines; `pl run log` prints the whole log. When a transition puts an issue in a status with a `dispatch.status` rule (Agent Review, `agent = "codex"`), the server writes a `dispatch` row, and a runner registered with that agent claims it as soon as the issue's running run has ended: no transition, a second run on the same branch and in the same worktree, running `codex app-server` with the status's prompt.

## Sub-features

- `register` makes a runner actor (role `runner`) and a `runner` row; `pl runner list` shows it with its last heartbeat, or `No runners.`. `runner.models` holds the `models` it sent, by agent key (`--model` as `claude-code`, `--codex-model` as `codex`).
- `agent-kinds`: `pl runner start --agents opncode` exits 1 with ``unknown agent kind `opncode`; the kinds are claude-code, codex, opencode, pi, cursor`` (a typo), and `--agents pi` with ``unsupported agent `pi`; this runner can run claude-code and codex`` (a kind it has no adapter for); both fail before registering, so `SELECT count(*) FROM runner` is unchanged. `POST /api/runners` with `{"name":"r","agents":["opncode"]}` answers 422 with the first text.
- `model`: a claim copies its agent's model from `runner.models` onto `attempt.model` (NULL when the runner sent none: the agent's own default). The API's runs and attempts carry it and the issue page shows it; `pl` does not print it.
- `heartbeat` updates `runner.last_heartbeat` and renews only the leases of the attempts the body lists in `held`; a claim the runner never received expires. The answer's `stale` lists the held attempts it did not renew (finished, or failed by `lease-expiry`); the runner stops their agents and its log says `run <id>: lease lost; stopping the agent`.
- `claim` moves `start → in_progress` as the runner, writes a `run` row and an `attempt` row with `attempt = 1`.
- `concurrency`: with `[dispatch] max_concurrent = N` in the active workflow, a claim made while the workspace has N `attempt` rows in `state = 'running'` answers 204, writes nothing, and leaves the issue in Start, whichever runner asks. A run waiting for its next attempt holds no slot; a lapsed lease holds one until the sweep fails it; `POST /api/runs/{id}/resume` is not a claim and answers 200 at the limit. A waiting claim at the limit retries any issue on each wake, so a `finish` lets it through within milliseconds; a raised limit is read at the runner's next poll. With no key there is no server limit, only each runner's `--max-concurrent`. `[dispatch.agent.<kind>] max_concurrent = N` (a table per agent kind, `[dispatch.agent.codex]`) limits one kind the same way, counted by `run.agent` over the workspace's running attempts: a runner is not offered that kind's work (an issue in Start when In Progress's agent is full) while N run, and gets other kinds' work in the claim order meanwhile; a claim that finds nothing while one of its kinds is full answers 204 and retries any issue on each wake. A claim needs room under both limits.
- `claim-taken` is what a second runner gets when it raced for the same issue: its log says `claim taken: PL-<n> was claimed by runner <name>`, and no second `attempt` row exists.
- `worktree` is a checkout under the runner's `--state-dir` (`worktrees/<owner>/<name>/<issue>`) on the issue's branch.
- `log` streams the agent's stdout (stream-json lines) and stderr (`stderr: ` prefix) to `run_log`. Each line carries its per-attempt `line_no`, so a resent batch is stored once.
- `finish` records `succeeded` or `failed`, `duration_ms`, `input_tokens`, `output_tokens` and `cost_usd`: Claude Code's `total_cost_usd` from its `result` line, digit for digit (`SELECT cost_usd::text FROM attempt`), `NULL` for Codex and for an attempt with no `result` line. Any `cost_usd` but `[0-9]+(\.[0-9]+)?` up to 30 characters answers 422 `cost_usd must be a decimal such as 0.0453`.
- `lease-expiry` fails an attempt whose runner stopped heartbeating with `lease expired: runner <name> stopped sending heartbeats`.
- `dispatch-on-entry` writes one `dispatch` row per transition into a status with a dispatch rule (`agent`, and the `transition_id` whose `to_status` it is for); the issue's next transition deletes one still unclaimed, and the claim sets its `run_id`. The claim from Start writes and claims its own row in one transaction.
- `dispatch-again` queues one more `dispatch` row when a run ends (`finish` with either outcome, or `lease-expiry`) and its issue has made no transition since the one that dispatched the run: same `transition_id` and `agent`, `run_number` one higher, written in the transaction that ends the run. It applies to every dispatch, so to the Claude Code run in In Progress too. A run that moved its issue, or whose issue a person or a GitHub event moved, queues nothing. Nor does a run that ends in a status the active workflow now locks to agents or runners, or no longer gives a dispatch rule. The limit is 3 runs per transition (`RUNS_PER_ENTRY` in `runs.rs`); a new transition into the status starts at `run_number` 1.
- `waiting-on-person`: after the third run of one entry ends with the issue still there, no row is queued, and `pl issue show` prints `waiting on a person: 3 runs in <status name> ended without moving it` after `Status:` and any `Parent:`, `Project:` and `Milestone:` lines (`waiting_on_person` in `GET /api/issues/{id}`; absent otherwise).
- `codex-run` is the run a runner started with `--agents claude-code,codex` gets for that row: `pl issue show` lists it above the Claude Code run as `Codex  runner <name>`, on the same branch, with token counts from Codex's `thread/tokenUsage/updated`. Its log is the app-server's JSON-RPC messages, without the streaming deltas.

## How to get to it (user POV)

- `pl run list <id>` lists each run's attempts with runner, outcome and reason; the run's line ends `tokens N in / M out  cost $<value>` when the latest attempt reported a cost.
- `pl runner start [--name N] [--state-dir DIR] [--agents claude-code,codex] [--model M] [--codex-model M] [--codex-effort E] [--codex-command PATH] [--max-concurrent K]`, `pl runner list`.
- `pl issue move <id> start`, then `pl issue show <id>` and `pl run log <run-id>`.
- `POST /api/runners`, `POST /api/runners/{id}/heartbeat`, `POST /api/runs/claim`, `POST /api/runs/{id}/log`, `POST /api/runs/{id}/finish`, `GET /api/issues/{id}/runs`, `GET /api/runs/{id}/log`.

## Driving it with control-punchlist

Preconditions:

- Baseline run `$RUN`. `up` bootstraps the workspace with repository `gannonh/punchlist-sandbox`, so runners clone and push only there.
- With `up`'s GitHub App credentials (the sandbox App, Contents and Pull requests: Read and write), runs act as the App and the runner needs no `gh` login. Without them a run uses the runner's own: then `gh auth status` shows a logged-in account that can push to the sandbox, and `git ls-remote https://github.com/gannonh/punchlist-sandbox.git HEAD` answers.
- An agent run makes a live model call. Start a runner that will claim an issue only inside a named live check. `$C runner` passes `--model haiku`, the alias for the newest Haiku (Haiku 5.5 on the Anthropic API), and `--codex-model gpt-6-luna` for Codex runs when this checkout's `pl` has that flag. A runner claims Codex dispatches only when started with `--agents claude-code,codex`, and then needs `codex` on `PATH`, logged in (`codex login status`).

- **Start a runner.** `$C runner "$RUN" r1`. It waits until the log at `$EVIDENCE/runner-r1.log` says the runner registered.
- **List.** `$C pl "$RUN" runner list`. One line naming `r1`, `claude-code` and a heartbeat a few seconds old. `$C sql "$RUN" "SELECT name, models FROM runner"` has one row, `r1 | {"codex": "gpt-6-luna", "claude-code": "haiku"}`. With no issue in Start this makes no model call; `$C runner-stop` prints `stopped runner r1`.
- **Model, without a model call.** Register through the API with `models` and claim, as [issue-refusals.md](issue-refusals.md)'s Gated recipe does: `-d '{"name":"r","agents":["claude-code"],"models":{"claude-code":"haiku"}}'`. `SELECT attempt, state, model FROM attempt` is `1 | running | haiku`. Nobody heartbeats that runner, so the attempt fails `lease expired: runner r stopped sending heartbeats` after 30 s and the run stays running: a real runner started afterwards in the same run claims attempt 2 and calls the model.
- **Claim.** `$C pl "$RUN" issue create --title "Add a hello file" --body "Create hello.txt containing hello."`, `$C pl "$RUN" issue move PL-1 todo`, `$C pl "$RUN" issue move PL-1 start`, wait 10 s, `$C pl "$RUN" issue show PL-1`. `Status: In Progress`, a timeline line `r1 (runner)  Start → In Progress`, and a run with agent `Claude Code`, runner `r1`, outcome `running`. `$C sql "$RUN" "SELECT issue_id, runner_id, attempt, state FROM attempt"` has one row.
- **Worktree.** `git -C /tmp/punchlist-verify/$RUN/runner/r1/worktrees/gannonh/punchlist-sandbox/PL-1 branch --show-current` prints `feature/pl-1`.
- **Log.** `$C pl "$RUN" run log <run-id>` while the agent works, and again after. The line count grows. After the run, a line contains `gh pr create`.
- **Finish.** `$C sql "$RUN" "SELECT state, duration_ms, input_tokens, output_tokens FROM attempt"` shows `succeeded` and non-null numbers. `with-env $C gh pr list --repo gannonh/punchlist-sandbox --draft --search "PL-1 in:title"` lists the agent's pull request.
- **Concurrency, without a model call.** Push `[dispatch] max_concurrent = 2` to the sandbox's `.punchlist/workflow.toml` on `main` (as [workflow-and-gates.md](workflow-and-gates.md) does) and wait for the `workflow_load` job. Move three issues to Start, register a runner through the API as **Model, without a model call** does, and claim three times right after each other (a lease is 30 s). The first two answer 200 and the third 204; `$C sql "$RUN" "SELECT count(*) FROM attempt WHERE state = 'running'"` is `2` and `SELECT status FROM issue WHERE id = 'PL-3'` is `start`. Hold a claim open (`{"wait_seconds":20}`) and `POST /api/runs/{id}/finish` one attempt after its agent moved the issue on (else `dispatch-again` gives the slot back to that issue, which numbers first): the held claim answers 200 for PL-3 within 2 s. Put the file back afterwards.
- **Contention.** `$C runner "$RUN" r1` and `$C runner "$RUN" r2`, then move one issue to Start. `$C sql "$RUN" "SELECT count(*) FROM attempt WHERE issue_id = 'PL-<n>'"` is `1`, and the losing runner's log has `claim taken: PL-<n> was claimed by runner <winner>`.
- **Codex on entry.** `$C runner "$RUN" r1 --agents claude-code,codex`, then the **Claim** steps with a body Claude Code can finish. When its run requests Agent Review, `$C pl "$RUN" issue show PL-1` lists a second run, `Codex  runner r1`, within seconds of the first one ending; `$C sql "$RUN" "SELECT r.agent, r.status, r.branch FROM attempt a JOIN run r ON r.id = a.run_id WHERE a.issue_id = 'PL-1' ORDER BY a.started_at"` shows `claude-code | in_progress` then `codex | agent_review` on one branch, and `SELECT t.to_status, d.agent, d.run_id IS NOT NULL FROM dispatch d JOIN transition t ON t.id = d.transition_id ORDER BY d.created_at` shows both rows claimed. With a passing check and no open thread the Codex run moves the issue to Human Review. A runner without `codex` in `--agents` leaves the `dispatch` row unclaimed (`run_id` NULL), as `main` before this slice left the issue: no run starts.
- **Dispatched again, to the limit.** Up to three short Codex runs. Before `up`, give the sandbox a review prompt that does nothing, the way the request-only prompt in [workflow-and-gates.md](workflow-and-gates.md) is swapped: save the current file (`with-env $C gh api repos/gannonh/punchlist-sandbox/contents/.punchlist/prompts/agent_review.md --jq .content | base64 -d > agent_review.orig.md`), then `with-env $C gh api -X PUT` that path on `main` with the file's `sha` and one line as `content` (base64): ``Do nothing: run no command, call no tool, and do not call `request_transition`. Reply with the single word `done` and stop.`` Then `PUNCHLIST_VERIFY_PORT=7879 with-env $C up`, wait for the `workflow_load` job, and check `$C sql "$RUN" "SELECT prompts->>'prompts/agent_review.md' FROM workflow_version"` shows that line. Start `$C runner "$RUN" r1 --agents claude-code,codex` and run the **Claim** steps. The Claude Code run opens the pull request and requests Agent Review; three Codex runs of about 6 s each follow back to back, and then nothing. `$C sql "$RUN" "SELECT t.to_status, d.agent, d.run_number, d.run_id IS NULL AS waiting, r.outcome FROM dispatch d JOIN transition t ON t.id = d.transition_id LEFT JOIN run r ON r.id = d.run_id ORDER BY d.created_at"` shows `in_progress | claude-code | 1` (one row: the run moved its issue) and `agent_review | codex` with `run_number` 1, 2, 3, none waiting; 40 s later `SELECT count(*) FROM run` is still `4`, and `$C pl "$RUN" issue show PL-1` prints `waiting on a person: 3 runs in Agent Review ended without moving it` under `Status: Agent Review`. On `main` before this slice the same flow stops at one Codex run. Afterwards `down`, close the pull request, and `with-env $C gh api -X PUT` the saved prompt back; its sha256 is then what it was.
- **Stop.** `$C runner-stop "$RUN" r1` sends SIGINT; a running attempt finishes `failed` with reason `runner stopped`, lost, so its run gets attempt 2. `down` stops every runner in the run.

## Gotchas

- Each run's runners clone the sandbox under `/tmp/punchlist-verify/<RUN_ID>/runner/<name>/`, which `down` deletes. Branches and pull requests the agent pushed stay in the sandbox: close the pull request and delete the branch after the check (`with-env $C gh pr close <n> --repo gannonh/punchlist-sandbox --delete-branch`).
- Sandbox branches are named after the issue id, and every run numbers issues from `PL-1`. Before a run, check `with-env $C git ls-remote --heads https://github.com/gannonh/punchlist-sandbox.git 'feature/pl-*'` and delete leftovers, or the agent's push collides.
- Contention is deterministic only when both runners are already long-polling when the issue enters Start: start both, wait for both to register, then move the issue.
- A claim for an issue that ran before gets the same branch name while no pull request on it has merged: the runner reuses the issue's worktree, or without one starts from the branch on the remote. A worktree directory deleted without git (`rm -rf`) is pruned from the clone and added again on the next claim, so the run does not fail on git's stale registration.
- Once the branch's pull request has merged and none is open on it, such as after a person moved the issue `merging → todo` following a refused merge, the claim names `feature/<id>-2` (then `-3`) and lists the issue's merged branches in `merged_branches`. The runner starts that branch from the default branch and replaces a clean worktree left on a merged branch; one with uncommitted or untracked files fails the run with `has uncommitted work on the merged branch`. The run opens a second pull request that lists only its own changes; `pl issue show` lists both, and the gates read the open one.
- The claim reads the recorded pull requests: a claim made before the merge's webhook arrives continues on the merged branch.
- A dispatch waits while the issue has a running run: the Claude Code run that requested Agent Review still has to exit. The claim follows its `finish` by milliseconds; measure from the run's `finished_at`, not only from the transition.
- A Codex run gets the person's sign-in from their Codex home and nothing else of theirs. The runner starts `codex app-server` with `CODEX_HOME` set to `<worktree root>/codex-home/<run id>`, a directory it makes for the run and removes when the run ends, holding only a link to the person's `auth.json` (from `$CODEX_HOME`, else `~/.codex`). Apps, plugins, hooks and skill dependency installs are off (`-c features.apps=false -c features.plugins=false -c features.hooks=false -c features.skill_mcp_dependency_install=false`). The model (`--codex-model`), the reasoning effort (`--codex-effort`, default `medium`), the sandbox (`danger-full-access`, no approvals) and Punchlist's MCP server are the runner's.
- The worktree is an untrusted project to Codex: a `.codex/config.toml` or hooks in the repository are not loaded, and neither is the repository's `AGENTS.md` (`"instructionSources":[]`). That is on purpose: the reviewing run takes no instructions from the tree it reviews. Its instructions are the workflow's prompt.
- Skills are not in Codex's home: Codex finds them in `~/.agents/skills` and in the worktree's `.agents/skills/` and `.codex/skills/`, trusted or not. The runner asks `skills/list` first and starts the thread with each one disabled, Codex's bundled ones off and no skill list in the instructions, so neither the person's skills nor one committed to the branch reaches the model, even when the prompt names it as `$name`. The answer to `skills/list` names the person's own skills and their paths, so it is kept out of the run log; the log has `disabled the <n> skills Codex found` in its place. The agent can still read a `SKILL.md` as a file, like any file in the worktree.
- With `--codex-model` unset a Codex run uses Codex's built-in default model, not the person's `model`. The person's `model_provider`, base URL, proxy and CA settings in `config.toml` do not reach the run either, so a setup that needs a provider other than Codex's default fails at the first turn.
- The runner's environment still reaches Codex, on purpose: `OPENAI_BASE_URL`, `OPENAI_API_KEY`, `CODEX_API_KEY`, `CODEX_ACCESS_TOKEN`, `CODEX_CA_CERTIFICATE` and `SSL_CERT_FILE` are inherited. Of these only `CODEX_ACCESS_TOKEN` signs `codex app-server` in, ahead of a stored sign-in; `CODEX_API_KEY` works for `codex exec` only, and the app-server takes no sign-in from `OPENAI_API_KEY`. `CODEX_SQLITE_HOME` is removed, so a run's state databases stay in its own home.
- In the run log, `grep -o '"method":"mcpServer/startupStatus/updated","params":{[^}]*' | grep -o '"name":"[^"]*"' | sort -u` lists the MCP servers the thread started, which is `"name":"punchlist"` alone, and the answer to `thread/start` (`{"id":2,"result":…`) carries `"reasoningEffort"` and `"instructionSources"`. A Claude Code run's `system` `init` line lists its servers in `mcp_servers`.
- A run whose person has no `auth.json` (not logged in, or a sign-in kept in the keyring) fails before Codex starts with `cannot make the Codex home: no Codex sign-in at <path> and no CODEX_ACCESS_TOKEN`, unless the runner's environment has `CODEX_ACCESS_TOKEN`: then the run's home has no link and Codex signs in from the variable. A runner that is killed outright leaves its running Codex runs' `codex-home/<run id>` behind: the link, Codex's state databases and `shell_snapshots/`, no copy of the sign-in. Under `/tmp/punchlist-verify` a Codex run's log has one `stderr: WARNING: proceeding, even though we could not create PATH aliases: Refusing to create helper binaries under temporary dir "/tmp"` line, because its home is under `/tmp`; the run goes on.
- A runner that still has the issue's worktree fast-forwards it to the branch on the remote before the agent starts, so a push by another runner or a person is there; a worktree that diverged from the remote fails the run with `cannot fast-forward to origin/<branch>`, and so does a remote that cannot be asked for the branch (`git ls-remote: …`); a branch the remote does not have yet is fine.
- A Codex thread is started `ephemeral`: Codex keeps no rollout of it under its home's `sessions`.
- A runner holds its token in memory only, and its name is its identity: `pl runner start` with the same name by the same person gets the same runner back with a new token (the old one answers 401). It reads `GET /api/runners/{id}/leases` and resumes each Claude Code attempt whose worktree is still on its branch (`claude --resume <session id>`, log lines numbered on from the stored ones); every other held attempt is finished `failed`, `runner restarted`, lost. A lost attempt (that, `runner stopped`, or a lease expiry) gets attempt 2 of the same run, which any runner claims; a second loss fails the run and `dispatch-again` applies. `$C runner-signal "$RUN" r1 KILL` is the crash; `STOP` freezes a runner as a stale writer.
- Any run that ends without moving its issue is followed by another, up to three per entry: `runner-stop` in the middle of a run, an agent that gives up, or an issue body that never asks for a pull request each cost up to three model runs while a runner that can run the agent is up. To stop that, stop the runner or move the issue (`pl issue move PL-<n> todo`).
- A lease that expires queues the next dispatch without waking long-polling runners; it is claimed at the runner's next poll, up to 30 s later. A `finish` wakes them at once.
