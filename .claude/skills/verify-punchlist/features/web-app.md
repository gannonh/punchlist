# Web app: the issue list, the board and the issue page

A signed-in person opens the server's URL and sees the workspace's issues grouped by status (List, key `1`) or in one column per status (Board, key `2`). Each row shows the id, title, labels, assignee (a person, an agent with its kind, or Unassigned), run state, pull request state with checks, and the gate summary of the next gated transition. Statuses no agent may act in carry a "people only" badge. The list stays current through the workspace's event stream: a move made with `pl`, a claim, the end of a run, a pull request delivery, a check run or proof shows without a reload. `Enter` on a row opens its issue page, `/issues/<id>`.

## Sub-features

- `web-sign-in`: `/sign-in` takes a person's token and sets the `punchlist_session` cookie; any other token answers `That is not a person’s token.`
- `web-hide-closed`: the `hide Done and Canceled` checkbox (named from the workflow's closed statuses) is checked by default, and leaves those statuses' issues out of the list, the board and the shown number in the count. The board keeps their columns, empty.
- `web-list`: one section per non-empty shown status (`[data-group=<key>]`), in workflow order, rows `[data-issue=<id>]`. Each row holds `[data-assignee]`, `[data-run]`, `[data-pr]` and `[data-gates]`.
- `web-board`: one column per workflow status (`[data-column-section=<key>]`), empty ones showing `No issues`. Below 768 px one column shows at a time, picked from a status strip (`[role=tab][data-column]`).
- `web-filter`: the `Filter issues` box matches id, title, labels, assignee (an agent's kind name too) and status name; the `Assignee filter` select takes Everyone, People, Agents, one agent kind, or Unassigned; the `Project filter` select takes Any project, No project or a project, and the `Milestone filter` select Any milestone, No milestone or a milestone as `Project · Milestone`, only the chosen project's when one is chosen (choosing a project clears a milestone outside it). Both fill from `GET /api/projects` once it answers, and the list does not wait for it. The `Label filter` and `Status filter` buttons open menus of checkboxes (role `menuitemcheckbox`; a toggle keeps the menu open, `Escape` closes it): the distinct labels of the rows, sorted, and the workflow's statuses in order. Their text reads `Labels` or `Labels: idea, ui`, and `Statuses` or `Statuses: Backlog, Todo`, in menu order. An issue matches the labels when it has every chosen one, and the statuses when its status is one of them. Chosen statuses replace `hide Done and Canceled`, so choosing Done shows Done issues, and on the board only their columns show. An issue shows only when it matches every filter. The project, milestone, label and status filters live in the URL (`/?layout=board&project=<id>&milestone=<id>&label=idea&label=ui&status=todo`, `none` for No project or No milestone, a list as the key repeated), so a link or a reload keeps them and the layout switch keeps them; an id the select does not list shows as `Unknown project` or `Unknown milestone`. Text and assignee are not in the URL. Nothing matching a filter shows `[data-empty]` with `Nothing here` and `Clear filters`, which clears them all and leaves only `layout` in the URL; with no filter and every issue hidden as closed, it says `Every issue is in Done or Canceled, which are hidden.` with `Show them`. From 3 characters the `Filter issues` box also asks `GET /api/search` 150 ms after the last keystroke, and shows the rows of its hits under the other filters too, with a body or comment hit's snippet on one line under the title: `[data-snippet]`, its text the field (`body` or `comment`) then the line, the match in `mark`, `white-space: nowrap`. Nothing is requested under 3 characters, and clearing the box removes the snippets at once. `Esc` leaves the box with its text. The count reads `<shown> of <total>` (`[data-count]`), where shown leaves out hidden closed issues. In a script, wait for `[role=menu]` to be gone after `Escape` before clicking a trigger again: a click while the menu is still closing does not reopen it.
- `web-keys`: `j`/`k` (or arrows) move the selection (`aria-selected="true"` on one `[data-issue]`), `Enter` opens the issue page (`/issues/<id>`, or `/issues/<id>#seq-<n>` for a row whose snippet is a comment), a click on the selected row opens its side sheet, `s` opens the status menu, `/` focuses the filter, `1`/`2` switch layout (`?layout=board` in the URL). On the board `h`/`l` request a move of the selected issue one column left or right through `POST /api/issues/{id}/transitions`. Keys do nothing while a field, the sheet, a menu or the New issue dialog has focus.
- `web-create`: `New issue` opens a dialog (Title, Body); `Create issue` adds the row to Backlog when the server answers.
- `web-issue-page`: `/issues/<id>`. Selectors: `[data-transition=<to>]` with `data-verdict` `allowed`, `blocked` or `locked` (blocked ones hold `[data-blocked-gate]` and `[data-blocked-names]`), `[data-gate=<gate>]` with `data-pass` and an `[data-evidence]` link that scrolls to `#pr`, `#checks`, `#threads` or `#proof`, `#checks [data-check=<name>]` with `data-check-state`, `[data-run]` cards with `data-attempt`, `data-outcome` and `[data-log=live]` while running (`done` after; each log line an `li[data-line-kind=message|tool|result|error|event|plain]` whose `summary` opens its raw line, `[data-raw]`, and the box follows the newest line until scrolled up), `[data-proof=image|video|report]`, `[data-proof-input]` (file input), `[data-kind]` feed entries (`li#seq-<n>`, with `data-seq`) with `data-actor-type`; `#seq-<n>` in the URL scrolls that entry into view once the timeline loads and marks it `data-target` (not with the Transitions feed chosen, which leaves a comment out), `[data-feed=all|comments|transitions]`, the composer `[aria-label="New comment"]`, and `[data-notice=agent-locked|locked|waiting|done]`. The page's root is `[data-issue-page=<id>]` with `data-viewer` `person` or `agent`, and the header reads `Viewing as <name> (<role>)`. On this page `[data-transition]` is a status key and `[data-run]` a run id; on the list they are a row's state. Keys `g`, `t`, `c`, `Esc` (`Esc` in a field blurs it first, so leaving the composer takes two). To view as a standalone agent, open a Playwright context with `extraHTTPHeaders: {Authorization: 'Bearer <agent token>'}` (from `pl actor create --agent`); no sign-in. `GET /api/issues/<id>/transitions` is the JSON behind the moves ([workflow-and-gates.md](workflow-and-gates.md)).
- `web-issue-moves`: the viewer's own blocked move (`data-verdict=blocked`) has `aria-disabled="false"`: a click sends `POST /api/issues/{id}/transitions`, which reads GitHub first, so it moves or toasts `<id> did not move to <Status>. Refused (gate_failed): gate <gate> failed: <reason>`. A move another role makes is hidden, except the next gated move while one of its gates fails: a person sees the agent's In Progress → Agent Review or Agent Review → Human Review move as `blocked` with `aria-disabled="true"`. A `locked` move is disabled too; a disabled one only toasts its rule.
- `web-issue-pr-proof`: the pull request's title (`#pr a[target=_blank]`) links out only for a plain `https://github.com/<owner>/<repo>/pull/<number>` with the pull request's own number, and is plain text otherwise. An upload (`[data-proof-input]`, accepting the `PROOF_TYPES` extensions) sends the server's content type for its extension, so a `.log` the browser types as empty is stored as `text/plain`.
- `web-edit`: the side sheet edits Title, Labels and Parent (Enter or blur saves; an empty Parent clears it, and the parent's title shows under it), and Assignee, Project (`No project` or one of `GET /api/projects`) and Milestone (`No milestone` or one of the issue's project's, disabled without a project, its `PASS when` text under it). Another project clears the milestone. Edits show at once; a refused edit puts the old value back and toasts `<id> was not changed. Refused (<code>): <message>`. The selects are `[aria-label=Project]` and `[aria-label=Milestone]`; their options have role `option`. Projects and milestones come from `pl` ([issue-placement.md](issue-placement.md)).
- `web-transition`: a status change is not optimistic. The row shows `[data-transition=pending]` `Moving to <Status>…` until the server answers, then either moves or shows `[data-transition=refused]` `<Status>: Refused (<code>): <message>` (for `gate_failed`: `Refused (gate_failed): gate <gate> failed: <reason>`), and stays where it was.
- `data-last-seq` on the screen's root element is the last event sequence the app's cache applied, from the list or the stream. Compare it to `SELECT max(seq) FROM event`.
- `web-perf`: each commit of the list or board records a `pl:render` measure (`detail: {layout, rows}`), and each commit of the issue page one with `detail: {layout: 'issue', events, attempts}`, from the start of the view's render to its DOM update. Layout and paint are not included.

## How to get to it (user POV)

- The run's server URL, `SERVER_URL` in `run.env`, serving `web/dist`.
- `pnpm dev` serves the same app from Vite on `127.0.0.1:5173`, proxying `/api` to the server.

## Driving it with control-punchlist

Preconditions:

- `pnpm build` has written `web/dist` (the run links it, so a later rebuild is served on reload).
- A run started with `RUN=$($C up)`; for the T3 Code integrated browser, which runs on the Mac mini and cannot reach sartre's 127.0.0.1, start it bound to sartre's Tailscale address: `RUN=$(PUNCHLIST_VERIFY_HOST=$(tailscale ip -4) $C up)`.

- **Sign in.** `URL=$($C sign-in-url "$RUN")` prints `$SERVER_URL/sign-in-<random>.html`. Opening it posts the run's person token to `/api/session` and lands on `/` signed in. The token is never in the URL or the transcript; the page is removed after 2 minutes, so get a new URL per browser.
- **Headless.** Playwright from this repository (`node_modules/.pnpm/node_modules/playwright`) with the Chromium in `~/.cache/ms-playwright`: `page.goto(URL)`, then `page.waitForURL(u => u.pathname === '/')`. Read state from the DOM selectors above and from `$C sql`.
- **Integrated browser.** Load the preview tools with ToolSearch `select:mcp__t3-code__preview_open,mcp__t3-code__preview_click,mcp__t3-code__preview_evaluate,mcp__t3-code__preview_snapshot,mcp__t3-code__preview_type,mcp__t3-code__preview_press,mcp__t3-code__preview_resize,mcp__t3-code__preview_recording_start,mcp__t3-code__preview_recording_stop`, then `preview_open` the sign-in URL. Assert with `preview_evaluate`, for example `[...document.querySelectorAll('[data-group]')].map(e => e.dataset.group)`.
- **An issue in In Progress, without a model.** As the person: create it, move it to `todo` and `start`, then `$C curl "$RUN" -X POST -H 'content-type: application/json' -d '{"name":"r","agents":["claude-code"]}' "$SERVER_URL/api/runners"` and claim with the answer's `token`: `curl -s -X POST -H "Authorization: Bearer <runner token>" -H 'content-type: application/json' -d '{}' "$SERVER_URL/api/runs/claim"`. Keep the runner token out of evidence. `web/e2e/issues.spec.ts` does the same in code.
- **Pending then refused.** Select that issue, press `s`, pick Agent Review (the menu's options have role `menuitemradio`: `page.getByRole('menuitemradio', { name: 'Agent Review' })`). Pass when `[data-transition=refused]` reads `Agent Review: Refused (role_not_allowed): only an agent makes in_progress → agent_review, not a person` and `$C sql "$RUN" "SELECT count(*) FROM transition WHERE to_status = 'agent_review'"` is `0`. The server answers in milliseconds; to see the pending state, hold the request (`page.route`, as the e2e test does).
- **Project and milestone filters.** Make projects and milestones with `$C pl "$RUN" project create Alpha` and `$C pl "$RUN" milestone create A1 --project Alpha`, place issues with `$C pl "$RUN" issue edit PL-1 --project Alpha --milestone A1`, and read the ids with `$C pl "$RUN" project list` or `$C sql "$RUN" "SELECT id, name FROM milestone"`. Choose with `page.getByLabel('Milestone filter').selectOption({ label: 'Alpha · A1' })`. Pass when `[...document.querySelectorAll('[data-issue]')].map(e => e.dataset.issue)` is the rows of `SELECT id FROM issue WHERE milestone_id = '<id>' ORDER BY number` and `location.search` is `?milestone=<id>`. `web/e2e/issues.spec.ts` does the same in code.
- **Live stream.** With the app open, `$C pl "$RUN" issue move PL-1 todo`. Pass when `[data-group=todo] [data-issue="PL-1"]` exists within 2 s.
- **Live runs and pull requests.** With the app open, finish the claimed run through the API (`POST /api/runs/{id}/finish` with the runner token, `outcome` failed) and the row's `[data-run]` reads `Queued` within 2 s; claim again and it reads `Running · …`. Deliver a `pull_request` (`$C webhook`) for the issue's branch and `[data-pr]` reads `#<n> draft`, then `#<n> open` after `ready_for_review`. `SELECT seq, kind FROM event WHERE kind IN ('run', 'pull_request', 'proof')` has the rows behind them; `SELECT count(*) FROM pull_request_change` is `0` once the sweep ran. `web/e2e/issues.spec.ts` does the same in code.
- **Issue page.** With an issue in In Progress (above) and a draft pull request delivered for its branch (`$C webhook`, [github.md](github.md)): open `$SERVER_URL/issues/PL-1` signed in. `[data-transition="agent_review"]` has `data-verdict=blocked`, `aria-disabled="true"` and `[data-blocked-gate]` `pr_ready`. In a context with a standalone agent's bearer header (above), the same button has `aria-disabled="false"`; clicking it sends the POST, and the toast reads `PL-1 did not move to Agent Review. Refused (gate_failed): gate pr_ready failed: pull request #<n> is a draft`. Upload a `.log` with `setInputFiles({ name: 'run.log', mimeType: '', buffer })` as the person: `SELECT content_type FROM proof` has `text/plain`.
- **Search.** Seed an issue whose body says `ci_green` and one with a comment saying it (`$C pl "$RUN" issue comment`), type `ci_green` in `Filter issues`. Pass within 1 s when `[data-issue="<id>"] [data-snippet]` has `textContent` `body<the body>` and its `mark` text is `ci_green`. Press `Esc`, select the comment's row, press `Enter`: `location.hash` is `#seq-<n>` with `<n>` from `SELECT e.seq FROM event e JOIN comment c ON c.id = e.comment_id`, and `document.getElementById('seq-<n>').getBoundingClientRect()` lies inside the viewport. `web/e2e/issues.spec.ts` does the same in code.
- **Phone.** Resize to 390×844 on both layouts and on the issue page. Pass when `document.documentElement.scrollWidth <= document.documentElement.clientWidth`.
- **Render budget.** Seed issues through `POST /api/issues` (500 sequential requests take about 2 s), reload, then read `performance.getEntriesByName('pl:render').map(m => [m.duration, m.detail])`. The first entry with `rows: 500` is the list's first render after load.
- **E2E.** `pnpm e2e` builds the app, starts its own run, runs `web/e2e/` and stops the run.

## Gotchas

- The workflow has no transition to the column on the left of most statuses (no `todo → backlog`), so `h` usually shows a `no_transition` refusal; that is the transition endpoint answering, not a bug.
- The server looks for `index.html` once, at start. A run started before `pnpm build` ever ran serves only the API (`up` warns); build, then `down` and `up` again.
- The session cookie is `SameSite=Strict` and `Secure` only behind https, so plain http on the Tailscale address works. A browser on another origin (such as Vite on a different port with the API elsewhere) does not send it; use the run's URL or `pnpm dev`'s proxy.
- A delivery's `pull_request` event waits for the server's 250 ms sweep, and the stream polls every 500 ms, so a row follows a delivery within about 0.8 s. The stream sends a row as it is when the message goes out: two changes inside one poll show only the second.
