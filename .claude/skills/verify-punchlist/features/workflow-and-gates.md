# Workflow file, gated transitions and the agent's tools

The server loads `.punchlist/workflow.toml` and the prompts it names from the repository's default branch, as the GitHub App: once when `punchlist-server bootstrap` queues a load, and again on every push to the default branch that changes `.punchlist/`. Each valid version is stored by content hash in `workflow_version` and becomes active; an invalid one is refused with its line and key in the server log and on the workspace, and the previous version stays active. `GET /api/workflow` returns the last refusal (`refused`: commit, time, reason) and `pl workflow show` prints it as a `Refused   <sha>: <reason>` line under the active version; the next load that activates a version clears it. Until one loads, the workspace uses the built-in workflow. Every transition checks the lock, the role and the gates in one transaction, and records each gate's result in `transition_gate`. A failed gate answers 409 with `gate`, `reason`, `evidence` and every gate's result. Each claim creates an agent actor for its run; the runner hands its token to `pl mcp`, which Claude Code gets as the `punchlist` MCP server with the tools `get_issue` (which also lists the issue's refused transitions and its pull requests' unresolved review threads, inside its fence), `comment` and `request_transition`.

## Sub-features

- `workflow-show`: `pl workflow show` prints `Version   sha256:<hex>`, `Commit    <sha>` (or `built-in`) and `Statuses  backlog, todo, start, in_progress, agent_review, human_review, merging, done, canceled`.
- `workflow-load`: a push to `main` that changes `.punchlist/` adds one `workflow_version` row and makes it active. The server log says `loaded workflow sha256:… from gannonh/punchlist-sandbox main at <sha>`.
- `workflow-invalid`: an active version stored before a validation rule existed (such as one without `[dispatch.status.in_progress]`, loaded by a server built before KAT-3750) stays in force: `pl issue create` and `pl issue move` succeed and transitions record its hash. A move to Start also succeeds, and `pl issue move` adds a second line after `PL-<n>  Todo → Start`: ``warning: no runner can claim PL-<n> under the active workflow: line <n>, `<key>`: <problem>`` (the response's `warning`, omitted under a valid version); until a valid file is pushed no runner claims that issue (with the dispatch rule missing, every poll answers 204). `pl workflow show` adds, under `Version`, ``Invalid   line <n>, `<key>`: <problem>; in force until a valid .punchlist/workflow.toml is pushed``, with the text a push of that file is refused with; `GET /api/workflow` carries it as `invalid` (`null` when valid). The server log says, once per start, ``workspace <id>: the active workflow sha256:<hex> fails validation: line <n>, `<key>`: <problem>; it stays in force until a valid .punchlist/workflow.toml is pushed``. Pushing a valid file replaces the version and the `Invalid` line goes. A stored version that does not parse at all still answers 500.
- `workflow-refused`: a file that does not load leaves `workflow_version` and `pl workflow show` unchanged. The server log says ``refused .punchlist/workflow.toml on <repository> <branch> at <sha>: line <n>, `<key>`: <problem>``, such as ``line 26, `transition[3].gates[1]`: unknown gate `pr_redy`; gates are …``. The runtime reserves `start`, `in_progress`, the runner `start → in_progress` transition (with no gates: ``line <n>, `transition[<i>].gates[0]`: the transition from `start` to `in_progress` takes no gates; …``) and the `dispatch.status.in_progress` rule; a file that renames or drops one is refused the same way (``line 4, `statuses`: the runtime needs a dispatch rule for `in_progress` ``; a missing piece has no line of its own, so it is reported at `statuses`, while a transition without `runner` is reported at its `by`), so claims keep working. `require` on a transition without `on` is refused the same way (``line <n>, `transition[<i>].require[0]`: `require` only applies to a transition with `on`; …``). A file that drops a status some issue is in is refused the same way: ``refused .punchlist/workflow.toml on <place>: status in use is not in the workflow: `todo` by 1 issue(s)``.
- `schema`: `GET /api/workflow/schema.json` answers without a token with the JSON Schema; its `title` is `Punchlist workflow`.
- `gate-refused`: `request_transition` to `agent_review` while the pull request is a draft answers `Refused (gate_failed): gate pr_ready failed: pull request #<n> is a draft`, then each gate's result; `pl issue transition` prints `refused: in_progress → agent_review needs gate pr_ready: pull request #<n> is a draft`, then the same list. No `transition` row is written. `pl` and `request_transition` differ when a reason names something GitHub's users wrote (a check's name, a thread's file): `pl`, the API's `message` and `reason`, `pl issue show` and the stored `transition_gate.reason` and `refusal.reason` keep the one string, `… checks failed on <sha7>: `ok` (failure)`. `request_transition` never prints the API's `message` for a failed gate: its first line is `Refused (gate_failed): gate <gate> failed: <sentence>` (no `<from> → <to> needs gate`), the `Gates:` list has the sentence only (`  ci_green: fail (1 of 1 checks failed on <sha7>)`), then a notice and a fence `<untrusted-gates-<nonce>>` holding, under a line `<gate>:`, each name behind `> ` (`> `ok` (failure)`, `> <path>:<line>`) and, past five names, Punchlist's own line `and <n> more`. The API carries the parts apart in each gate result: `reason` is the sentence, `outside` at most five names (a check's cut at 80 characters, a path at 200) and `outside_more` the count of the rest (both omitted when empty); the top-level `reason` is the joined string. An older server sends no `outside`, and its `reason` is already the joined string, which `request_transition` cannot tell apart: upgrade the server before `pl` and `pl mcp` on the runners; until then a refusal reaches the agent as before this change.
- `gate-passed`: after `gh pr ready`, the same request moves the issue to Agent Review as `Claude Code (agent)`, and `transition_gate` holds `pr_open`, `pr_ready`, `pr_names_issue`, all `pass`.
- `review-gates`: `agent_review → human_review` checks `ci_green`, `mergeable`, `no_open_threads` and `proof_attached` over the issue's one open pull request. A refusal names the first that failed: `ci_green: 1 of 1 checks failed on <sha7>: `ok` (failure)` (or `… checks pending on …`, or `no check run has reported on commit <sha7>` right after a push), `mergeable: GitHub's merge state for pull request #<n> is unstable, not clean` (or `GitHub has not computed pull request #<n>'s merge state yet; request again`), `no_open_threads: 1 unresolved review thread on pull request #<n>: <path>:<line>`. `proof_attached` fails with `no proof is attached to PL-<n> for attempt <a>` until proof is attached in the current attempt (`pl proof attach`), then passes with `1 proof record is attached for attempt <a>`. An accepted request records the four results in `transition_gate`.
- `required-checks`: with `[gate.ci_green]` and `required = ["ok", { name = "deploy", app = "vercel" }]` in the active `workflow.toml`, `ci_green` also needs a run of each named check from its GitHub App on the head commit that concluded `success` (a bare name is GitHub Actions, `github-actions`; names and slugs match exactly). An unsatisfied one is refused first, whatever else ran: ``ci_green: 1 of 2 required checks have no successful run on <sha7>: `deploy` from `vercel` (no run)``; the parentheses read ``(ran from `github-actions`)`` when only another app has a run of that name (`an unknown app` for a row recorded before `check_run.app`), and the run's conclusion or status when its app's run did not succeed (`(failure)`, `(skipped)`, `(in_progress)`). A pass reads as without the table, `2 of 2 checks passed on <sha7>`. A required `github-actions` check also needs a runner behind its successful run and the default branch's workflow file (`actions-checks` below). A malformed entry is refused at load: ``line <n>, `gate.ci_green.required[<i>]`: a required check is a check's name, or `{ name = "…", app = "…" }` with the slug of the GitHub App that produces it; a name or slug is matched exactly, so it cannot be empty or start or end with a space``.
- `actions-checks`: on a gated request, when the active workflow requires a `github-actions` check and the head commit has a check run of such a name, the server also reads `GET /repos/{owner}/{repo}/actions/runs?head_sha=<sha>` and, for the runs in those check runs' suites, each run's `/jobs` (a workspace that requires none makes no Actions call and needs no Actions permission), and for each job with a runner the blob of the run's workflow file at the head commit and on the default branch (`GET …/contents/<path>`, with and without `ref`). `check_run.workflow_path` is set for a check run whose job a runner took and whose name, conclusion and commit are the job's, with `workflow_sha` and `workflow_default_sha`. A required `github-actions` check whose successful run has no `workflow_path` is refused ``1 of 1 required checks have no successful run on <sha7>: `ok` from `github-actions` (no workflow job ran it)``; one whose two blobs differ (or whose file the default branch lacks) is refused ``1 of 1 required checks have no successful run on <sha7>; a check counts only when its workflow file is the default branch's: bring this branch's copy up to date with the default branch, and a person merges a real workflow change there first: `ok` from `github-actions` (its workflow file `.github/workflows/ci.yml` differs from the default branch's)``. Every successful `github-actions` run of the required name has to pass both tests, so a second workflow's unchanged job of that name does not stand in. Of the runs of one name in one suite a completed one without a `workflow_path` is judged after the others (a queued or running one is not demoted), so a created check run does not hide the real run: the refusal is then the real run's `(failure)`. A failed read of the runs or jobs refuses with `github_unreadable` (the log says `cannot read workflow runs from GitHub`). A server without App credentials records no `workflow_path`, so every required GitHub Actions check is refused `(no workflow job ran it)`; so is `pl issue show`'s checklist for a commit no gated request has read yet.
- `gate-checklist`: `pl issue show` prints, between the pull requests and the timeline, `Gates for <status> → <next>`, one line per gate (`  ci_green: pass (<reason>)`) and `  n of 4 gates pass`, for the issue's next gated transition; `GET /api/issues/{id}/gates` returns the same, and 204 when the status has none (Backlog, Human Review). It reads what is recorded then, without asking GitHub, so a request can answer differently.
- `event-gate`: gates on an `on = "pr_merged"` or `on = "pr_closed_unmerged"` transition are evaluated when the event arrives. With `gates = ["pr_names_issue"]` on `merging → done`, merging moves the issue and `transition_gate` holds `pr_names_issue | pass`. With `gates = ["ci_green"]` (any gate that needs the open pull request: the merge closed it) the issue stays in Merging, no `transition` row is written and the event is not tried again. One `event` row of kind `refusal` is written with the pull request row, and `pl issue show` prints it in the timeline: `<time>  <GitHub login> (github)  refused Merging → Done: gate ci_green failed: no open pull request is linked to PL-<n>: pull request #<n> is merged  [delivery <id>]` (no `[delivery …]` when the server read the merge from GitHub itself). The server log says the same with `issue=PL-<n>` and `actor=<GitHub login>`. A person then moves the issue out with `pl issue move PL-<n> todo`.
- `agent-comment`: a comment through MCP ends with `(agent)` on its own line in `pl issue show`.
- `agent-scope`: an agent token works only while its run is running, only on `/api/issues/<its run's issue>` and below (any other endpoint answers 403 `an agent acts only on its run's issue, PL-<n>`), and not on an issue in a status the workflow locks to agents (`human_review`).

## How to get to it (user POV)

- `pl workflow show`; `GET /api/workflow`; `GET /api/workflow/schema.json`.
- `pl issue transition <id> <status>` (alias of `pl issue move`); `pl issue comment <id> --body <text>`; `POST /api/issues/{id}/transitions`; `POST /api/issues/{id}/comments`.
- In a Claude Code run started by `pl runner start`: the MCP tools `mcp__punchlist__get_issue`, `mcp__punchlist__comment` and `mcp__punchlist__request_transition`.

## Driving it with control-punchlist

Preconditions:

- The GitHub App has **Contents: Read-only**, **Checks: Read-only** and **Actions: Read-only**, and subscribes to **Push**, on top of what [github.md](github.md) needs.
- The run reads the sandbox as the App: `PUNCHLIST_VERIFY_PORT=7879 with-env $C up`. `with-env` supplies `GITHUB_APP_PRIVATE_KEY` and the webhook secret; `up` sets `GITHUB_APP_ID=5254938` when the key is present. Without the key the server log says `no GitHub App credentials`, the load job fails with `no GitHub App is configured`, and every check that needs a load is skipped.
- The sandbox's `main` carries the PRD's `workflow.toml` and the prompts in `.punchlist/prompts/` (copy them from this repository's `.punchlist/`).

- **Loaded at bootstrap.** After `up`, poll `$C sql "$RUN" "SELECT state FROM job WHERE kind = 'workflow_load'"` until `done`. `$C pl "$RUN" workflow show` prints the hash and nine statuses, and `$C sql "$RUN" "SELECT hash, commit_sha FROM workflow_version"` has one row whose hash matches. On `main` before this slice, `pl workflow show` fails with clap's `unrecognized subcommand 'workflow'`.
- **Refused.** Push a commit to the sandbox's `main` that renames a gate in `.punchlist/workflow.toml` (such as `pr_ready` to `pr_redy`). Wait for the push delivery's job (`SELECT kind, state FROM job ORDER BY id`). `pl workflow show` prints the same hash and a `Refused` line with the pushed commit and reason, `SELECT count(*) FROM workflow_version` is unchanged, and `grep refused /tmp/punchlist-verify/$RUN/server.log` names the line and key. Revert the commit afterwards; the revert loads back the earlier hash without a new row and the `Refused` line is gone. For the dropped-status refusal, rename `todo` (every occurrence) with PL-1 in Todo: the log line names `todo` and the count, and PL-1 still moves; with no issue in Todo the same file loads.
- **Gate refused, then passed.** Start a runner (`$C runner "$RUN" r1`), create an issue whose body tells the agent to open a draft pull request, request Agent Review through `request_transition` while it is still a draft, then run `gh pr ready` and request again. In `$C pl "$RUN" run log <run-id>`, find the `tool_result` for the first `mcp__punchlist__request_transition`: it names `pr_ready` and `pull request #<n> is a draft`. Then `$C pl "$RUN" issue show PL-1` shows `Claude Code (agent)  In Progress → Agent Review`, and `$C sql "$RUN" "SELECT g.gate, g.result FROM transition_gate g JOIN transition t ON t.id = g.transition_id WHERE t.to_status = 'agent_review' ORDER BY g.position"` lists the three gates as `pass`.
- **Review gates, refused then accepted.** A Codex run that follows the workflow's prompt fixes the check and resolves the threads before it asks, so it is never refused. To see the refusals, give the sandbox a review prompt that only asks: commit a `.punchlist/prompts/agent_review.md` to the sandbox's `main` that says to call `request_transition` with `to` set to `human_review`, run `sleep 20` after a refusal and ask again, and to change nothing; wait for its `workflow_load` job; restore the real prompt afterwards (`workflow.toml` itself stays as it is). Start `$C runner "$RUN" r1 --agents claude-code,codex` and create an issue whose body has Claude Code add a file and an empty `ci-fail` at the repository root: the sandbox's `ok` check fails on a branch that has that file. While Codex loops, read `sed 's/\x1b\[[0-9;]*m//g' /tmp/punchlist-verify/$RUN/server.log | grep refused:`. First: `needs gate ci_green: 1 of 1 checks failed on <sha7>: `ok` (failure)`, with the issue still in Agent Review. Then open a thread (`gh api repos/gannonh/punchlist-sandbox/pulls/<n>/comments -f body=... -f commit_id=<head sha> -f path=<file> -F line=1`) and delete `ci-fail` on the branch (`gh api -X DELETE repos/gannonh/punchlist-sandbox/contents/ci-fail -f branch=<branch> -f sha=<blob sha> -f message=...`): once the new commit's check passes the refusal is `needs gate no_open_threads: 1 unresolved review thread on pull request #<n>: <file>:1`, `$C sql "$RUN" "SELECT count(*) FROM review_thread WHERE resolved = false"` is `1`, and `pl issue show` prints `3 of 4 gates pass`. Resolve the thread (GraphQL `resolveReviewThread`): the next request moves the issue to Human Review, and `$C sql "$RUN" "SELECT g.gate, g.result FROM transition_gate g JOIN transition t ON t.id = g.transition_id WHERE t.to_status = 'human_review' ORDER BY g.position"` lists the four gates as `pass`. The tool results are in `$C pl "$RUN" run log <codex run id>`.
- **Gate on a GitHub event.** Push a commit to the sandbox's `main` that adds `gates = ["ci_green"]` (or `["pr_names_issue"]`) under `on = "pr_merged"` in `.punchlist/workflow.toml`, and wait for the load. With an issue in Merging, merge its pull request. Failing gate: `$C sql "$RUN" "SELECT count(*) FROM transition WHERE to_status = 'done'"` shows `0`, the issue is still in Merging, `$C sql "$RUN" "SELECT kind, count(*) FROM event WHERE issue_id = 'PL-1' GROUP BY kind"` shows `refusal | 1` beside the earlier transitions (and the `run` and `pull_request` rows, which only update the web app's row), and `$C pl "$RUN" issue show PL-1` prints the `refused Merging → Done: gate ci_green failed: …` line. Then `$C pl "$RUN" issue move PL-1 todo` prints `PL-1  Merging → Todo` and the timeline shows that move after the refusal. Passing gate: `$C sql "$RUN" "SELECT g.gate, g.result, g.reason FROM transition_gate g JOIN transition t ON t.id = g.transition_id WHERE t.to_status = 'done'"` shows `pr_names_issue | pass | pull request #<n>'s branch names PL-<n>`. Redelivering the merge leaves every count unchanged. Revert the commit afterwards.
- **Required checks.** No model is needed: make the requests as an agent through the API ([github.md](github.md), "A gated request without a model call"; an attempt's lease is 30 seconds, so make each request right after its claim). Append `[gate.ci_green]` and `required = [...]` to the sandbox's `.punchlist/workflow.toml` on `main` (`gh api -X PUT repos/gannonh/punchlist-sandbox/contents/.punchlist/workflow.toml`), wait for the push's `workflow_load` job and the new hash in `pl workflow show`, and restore the file to its exact earlier content afterwards (compare `sha256sum`). The sandbox's two workflows give a pull request two runs named `ok`, both from `github-actions`; a branch that deletes `.github/workflows/ci.yml` and `ci2.yml` has none. `$C sql "$RUN" "SELECT name, app, conclusion FROM check_run WHERE head_sha = '<sha>'"` shows the runs and the app behind the reason.
- **A changed workflow file and a created check run.** As for required checks, with `required = ["ok"]` on the sandbox's `main`; no model. Each pull request names its issue by branch (`feature/pl-<n>-…`), is claimed as an agent and requests `human_review` right after the claim. `$C sql "$RUN" "SELECT id, name, conclusion, check_suite_id, workflow_path, workflow_sha, workflow_default_sha FROM check_run WHERE head_sha = '<sha>' ORDER BY id"` is the evidence behind each answer. (a) Changed workflow: on the branch, replace the steps of job `ok` in `.github/workflows/ci.yml` with `- run: "true"`; both `ok` runs succeed on runners, `ci.yml`'s with `workflow_sha` unlike `workflow_default_sha`, and the refusal names `.github/workflows/ci.yml` and says to bring the branch's copy up to date with the default branch, and that a person merges a real workflow change there first (`ci2.yml`'s unchanged `ok` does not stand in: every successful run of the required name has to count). A server from before this check accepts the same request. (b) Created check run: a branch that adds `ci-fail` and deletes `.github/workflows/ci2.yml` (one real `ok`, failing) and its pull request; then push a second branch, not a pull request, with one more workflow, `on: push` to that branch with `permissions: checks: write` and one step, `gh api -X POST repos/${{ github.repository }}/check-runs -f name=ok -f head_sha=<the pull request's head sha> -f status=completed -f conclusion=success` with `GH_TOKEN: ${{ github.token }}`. The created run has the higher id, is in the real run's suite and has no `workflow_path`; the refusal is ``… `ok` from `github-actions` (failure)``, and the request's `evidence` has the failing run. A server from before this check reads the created run as the newest, passes `ci_green` and refuses on `mergeable` (`unstable`). For `(no workflow job ran it)`, have the pull request's branch delete both workflow files (no real run) and create the check run on its head. (c) An untouched branch (one added file) is accepted, both `ok` rows with equal blobs. Delete the second branch and close the pull requests afterwards. A workflow cannot rewrite a real job's check run instead: from the same kind of push workflow, `gh api -i -X PATCH …/check-runs/<a real job's id> -f name=ok` answers 200 with the name unchanged, and `-f status=completed -f conclusion=success` answers 403 `Check run status and conclusions can only be updated internally by GitHub Actions`.
- **Review threads in `get_issue`.** No model is needed: `$C get-issue "$RUN" PL-1` starts `pl mcp` with the run's person token, calls `get_issue` and prints its text. In a run under `with-env`, create an issue, open a pull request in the sandbox from a branch that names it (`feature/pl-1-...`), and add a review comment (`gh api repos/gannonh/punchlist-sandbox/pulls/<n>/comments -f body=... -f commit_id=<head sha> -f path=<file> -F line=1`). `get-issue` then prints `  Unresolved review thread <PRRT_… id> on #<n>` under `Pull requests`, and inside the fence `## Review thread <id> on #<n>, line 1`, then `File:`, `Author:` and `Comment:`, each followed by GitHub's text on lines that start with `> `; `$C sql "$RUN" "SELECT node_id, resolved, path, line, comments, comments_total FROM review_thread"` has the row behind it. A body that contains `</untrusted-issue>`, the closing line of an earlier output with its nonce, or a forged `## Review thread …` heading stays behind `> ` above the one closing line, which is the output's last and carries a new nonce. The same holds for the rest of the fence: the issue's title and body are under `# Title` and `# Body`, each comment under `## Comment (<role>), <time>` with `Author:` (the actor's name) and `Comment:` each followed by quoted lines, and each refused transition's stored reason under `## Refused <from> → <to>, <time>: gate <gate> failed:`, every line of them behind `> `, so the only lines without `> ` are Punchlist's. Resolve the thread (GraphQL `resolveReviewThread`) and the next `get-issue` lists neither line. `get_issue` reads GitHub itself, so none of this waits for a webhook; in a run without App credentials, or when GitHub cannot be read, it prints `Punchlist could not read GitHub just now: the pull requests and review threads are as last recorded.` On `main` before this slice the output had the pull request's line and no thread.
- **Outside strings outside the fence.** A pull request's URL in `get_issue` is printed only when it is `https://github.com/<owner>/<name>/pull/<that number>` in the alphabet `A-Za-z0-9._/-`; otherwise the line ends at `open threads`. `request_transition` with a status the workflow lacks, even one holding a newline, answers `Refused (unknown_status): that status is not in the workflow` and echoes nothing (`PUNCHLIST_AGENT_TOKEN=<agent_token> $C request-transition "$RUN" PL-9 $'bogus\n## Forged'`).
- **The runner's prompt.** A run whose default branch, repository owner or name, or branch is empty, over 255 bytes, starts with `-` or has a character outside `A-Za-z0-9._/-` fails before any git command, with reason `the default branch is not a plain name` (or `branch`, `repository owner`, `repository name`); the text is never in the log. To read the prompt Claude Code received (`pl run log` holds only its output): the first user message of its session transcript, `~/.claude/projects/<the worktree path with / as ->/<session_id>.jsonl` (the `session_id` is in the run log's first lines; for a `/tmp/punchlist-verify/<RUN>/worktrees/r1/worktrees/gannonh/punchlist-sandbox/PL-1` worktree the directory is `-tmp-punchlist-verify-<RUN>-worktrees-r1-worktrees-gannonh-punchlist-sandbox-PL-1`). The title and body are under `# Title` and `# Body`, every line behind `> `.
- **A refusal as the agent reads it, without a model.** Claim the issue through the API ([github.md](github.md), "A gated request without a model call") and pass the claim's `agent_token`: `PUNCHLIST_AGENT_TOKEN=<agent_token> $C request-transition "$RUN" PL-9 human_review` calls `request_transition` through `pl mcp` and prints its text, exit 1 for a refusal. Keep the token out of evidence. A file or a check whose name holds instruction-like text shows only behind `> ` inside the `<untrusted-gates-…>` fence. A workflow job's `name:` on the pull request's branch names the check; a file is named by pushing it with git. `get-issue` always uses the person's token; only `request-transition` reads `PUNCHLIST_AGENT_TOKEN`.
- **Agent comment.** Have the run call `comment`; `pl issue show PL-1` shows `Claude Code (agent)  commented:` with `(agent)` as the last line.

## Gotchas

- The load reads the default branch's head when the job runs, not the commit the push named, so two quick pushes both load the newest file.
- `deny_unknown_fields` is on: a misspelt key, such as `gate` for `gates`, is refused rather than loaded without its gates.
- A refused file leaves no `workflow_version` row; the server log and the workspace's last-refusal columns (`workflow_refused_*`, shown by `pl workflow show`) record it. A refusal is final for that push: nothing retries it when the issue later leaves the status; the next push that changes `.punchlist/` loads the file.
- A gated request reads the issue's pull requests and their review threads from GitHub first, as the App, because webhooks reach the server seconds after GitHub and none is sent for a new review thread. A request made right after `gh pr create` or `gh pr ready` therefore sees the new state. If that read fails (a transport error, a 5xx, a timeout, a rate limit), the request is refused with 503 `github_unreadable`: `GitHub could not be read, so the gates for PL-<n> were not checked and it did not move; request again`; no gate result is recorded, and the server log says `cannot read pull requests from GitHub: …` (or `review threads`, for an open pull request's, on any gated transition). The reads are the repository's 30 most recently updated pull requests, then each one recorded for the issue and each open one that names it; a closed pull request never recorded for the issue is not read. One that GitHub answers 404 or 410 for is gone, and its recorded row stands. A run without App credentials reads nothing and judges the recorded rows. A recorded pull request that GitHub now reports closed or merged is recorded so before the request is judged, and moves the issue as its webhook would have, if the workflow has a transition on the event from the issue's status; the webhook changes nothing when it arrives. That transition has no `delivery_id`, so `pl issue show` prints no `[delivery …]` after it. Its actor is whoever merged, or `GitHub (github)` for a close without a merge, which GitHub's pull request does not attribute; the comment then reads `Pull request #<n> was closed without merging.` A closed or merged pull request that was never recorded for the issue is left to its webhook.
- A request whose evidence changed between its read of GitHub and the evaluation of its gates (a webhook delivery, or another read of the same pull request, recorded in that window with something the gates read different) answers 503 `evidence_changed`: `what GitHub has for PL-<n> changed while its gates were being checked, so nothing was decided and it did not move; request again`. The log says `evidence changed after it was read from GitHub`, no gate result is recorded, and the next request reads again. `github_unreadable` is only for a read of GitHub that failed. [github.md](github.md) has the recipe that holds a request there.
- So a refused request (409 or 401) can still have moved the issue: read the issue's status rather than assume nothing changed. Under the PRD's workflow a merge moves an issue only from Merging, so a merge read this way refuses at `pr_open` with `no open pull request is linked to PL-<n>: pull request #<n> is merged` and moves nothing. A close without a merge moves In Progress or Agent Review to Todo and ends the run, and the request is then answered 401 `missing or unknown bearer token`, as it would be after that webhook: the agent's token ended with its run.
- If a pull request read from GitHub cannot be recorded (a database error), the request fails with 500 and the server log says `database error`; it does not fall back to the recorded rows the way an unreadable GitHub does, because the gates could then pass on a pull request known to be closed. Ask again.
- `merging → todo` needs no refusal first. A pull request that merges after a person moved its issue to Todo is recorded `merged` and moves nothing: the workflow has no `pr_merged` transition from Todo, so no `transition` or `refusal` row is written and the issue stays in Todo.
- A gated request also reads the check runs on each open pull request's head commit from GitHub (`GET /repos/{owner}/{repo}/commits/{sha}/check-runs`, needs the App's Checks: read permission) and records them with the deliveries' rows, so `ci_green` does not wait for a `check_run` delivery; a failed read refuses the request with `github_unreadable` (the log says `cannot read check runs from GitHub`). The newest run of each name from each app in each check suite counts (`check_run.check_suite_id`; rows recorded before the column have none and group by name and app). Without App credentials only deliveries are recorded. A stopped server can therefore be given a failing or passing check and judge it on the next request; `SELECT name, check_suite_id, conclusion FROM check_run` shows what it read.
- GitHub computes the merge state when the pull request is read, so the first request after a push can be refused on `mergeable` with `has not computed … yet; request again`; the next one has it. A failing or pending check makes the state `unstable`, so `mergeable` fails beside `ci_green`.
- The agent token ends with its run. To re-request after the run finished, start a new run; a person's token cannot make `in_progress → agent_review`.
