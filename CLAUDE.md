# Punchlist

Punchlist is an open-source issue tracker where coding agents do the work and the tracker enforces how the work gets done. It is for solo developers and small teams that run several coding agents in parallel.

- Product spec: `docs/product/prd.md` (vision, principles, the workflow model, non-goals). The requirements are epics in the Punchlist workspace (`R<n>: …`, labeled `epic` and `P0` to `P3`, with their slices as children), and the roadmap is its milestones.
- Decisions: `docs/adr/`. Read the relevant ADR before changing what it decided.
- Work: Punchlist runs from its own Punchlist instance (`docs/dogfood.md`): workspace `Punchlist`, issues `PL-<n>`, read and moved with `pl` (`PUNCHLIST_CONFIG=~/.config/punchlist/punchlist.toml` on sartre) or the app at `https://sartre.tail984796.ts.net:7880`. Where the global rules say Linear, read this instance. The Linear project **Punchlist** in the Kata-sh team is read-only since the KAT-3792 cutover; its issues were imported, each showing its `KAT-<n>` id. A long-lived orchestrator session on sartre plans, grooms, watches and reviews the runs and never implements an issue itself (`docs/dogfood.md`, A day).

## Stack

- Backend: Rust in one Cargo workspace (ADR 0003). `punchlist-core` is pure and holds the workflow types and parser, the gates and the transition rules. The server, runner, `pl` CLI and MCP server depend on it. Postgres is the store.
- Rust libraries (ADR 0007): tokio and axum 0.8 with tower-http; sqlx for Postgres, with compile-time checked queries, committed `.sqlx/` offline data and SQL migrations run at server start; a Postgres `job` table claimed with `FOR UPDATE SKIP LOCKED` for background jobs; clap 4 for CLIs; `toml` with spans and schemars for the workflow file; rmcp for MCP; serde, thiserror, anyhow, tracing and reqwest.
- Runner (ADR 0005): `punchlist-runner` holds modules copied from Kata Symphony's orchestrator in `~/dev/kata-symphony/apps/symphony` at commit `e7c160f5`, each marked with its source path. The runner has no database; the server holds runs, attempts and leases.
- Frontend: a web app in TypeScript, React and Vite, served by the Rust server (ADR 0004). TanStack Router and TanStack Query; server state with optimistic field edits, pending transitions and a Server-Sent Events stream from the event log (ADR 0006). Tailwind with shadcn/ui, as in Groundwork.
- API types (ADR 0008): `punchlist-api` types derive utoipa schemas, utoipa-axum builds the OpenAPI document from the router, and openapi-typescript and openapi-fetch give the web app a typed client. `pnpm gen:api` regenerates `web/src/api/`; CI fails when it is stale.
- Data model (ADR 0010): one GitHub repository per workspace in v1. The active workflow is `.punchlist/workflow.toml` on that repository's default branch.
- License: MIT or Apache-2.0 (ADR 0002). Every crate sets `license = "MIT OR Apache-2.0"`.

### Layout and commands

The target layout (ADR 0009). A crate or directory is created by the first slice that needs it.

```text
Cargo.toml, rust-toolchain.toml, package.json, .sqlx/
crates/punchlist-core/     pure workflow, gates and transition rules; builds for wasm32
crates/punchlist-api/      API request and response types
crates/punchlist-server/   axum server, migrations/, jobs; binary punchlist-server
crates/punchlist-client/   Rust API client
crates/punchlist-runner/   runner from Symphony's orchestrator
crates/punchlist-mcp/      MCP server over stdio
crates/punchlist-cli/      binary pl
web/                       React app; src/api/ is generated
.punchlist/                Punchlist's own workflow and prompts
docker-compose.yml         Postgres for development; the self-host stack
```

Exists today: `punchlist-core`, `punchlist-api`, `punchlist-server`, `punchlist-client`, `punchlist-runner`, `punchlist-mcp`, `punchlist-cli`, `web/` and `.punchlist/`. `web/` is the pnpm workspace package `@punchlist/web` (`pnpm-workspace.yaml`): `src/api/` (generated `openapi.json` and `schema.d.ts`, and `client.ts`, the only way the app calls the API), `src/model/issues.ts` (pure: what a row shows, the refusal text, filters, grouping, and the stream-fed cache), `src/model/issue-page.ts` (pure: the issue page's gate summary, actor marks, feed filter, moves and spec), `src/lib/queries.ts` (TanStack Query: the cached list, the event stream, optimistic edits, pending transitions, and the issue page's reads under the key `['issue', id]`), `src/model/pull-requests.ts` (pure: the Pull requests page's sections and merge labels), `src/screens/` (sign-in, the issue list and board, the issue page and the Pull requests page), `src/components/` (the app header, rows, sheet, status menu; `ui/` is shadcn/ui, restyled only through the theme variables in `src/styles.css`) and `e2e/` (Playwright; shared helpers in `support.ts`).

- Rust comes from rustup, which reads `rust-toolchain.toml`. Both machines get it from devops' `bin/machine-setup`.
- `pnpm dev`: Postgres in Docker on `127.0.0.1:5433`, the server on `127.0.0.1:7878`, and Vite on `127.0.0.1:5173` proxying `/api` to the server; open the app at Vite's URL. `PUNCHLIST_VITE_HOST` (such as `$(tailscale ip -4)`) and `PUNCHLIST_VITE_PORT` move Vite; `PUNCHLIST_DEV_VITE=0` leaves it out, and the server serves `web/dist`. Local defaults for `DATABASE_URL` and `PUNCHLIST_BIND` are in `scripts/env.sh`; they are not secrets.
- `pnpm check`: the web app's dependencies, the `pnpm gen:api` staleness check, the web typecheck, lint and Vitest unit tests, then rustfmt, clippy with `-D warnings`, `punchlist-core` for wasm32, `cargo test` (starts Postgres; the sqlx tests need it), and the `.sqlx/` staleness check. Run it before a pull request. CI runs the same script, then `pnpm build`.
- `pnpm gen:api`: after changing an API type or route, write `web/src/api/openapi.json` (`punchlist-server openapi`) and `schema.d.ts` (openapi-typescript), and commit both.
- `pnpm build`: builds the web app into `web/dist`. `pnpm e2e` builds it, starts a server on a fresh database with verify-punchlist's `up`, runs Playwright (`web/e2e/`, the Chromium in `~/.cache/ms-playwright`, so `@playwright/test` stays on 1.63) and stops it.
- The browser signs in at `/sign-in` with a person's token (`POST /api/session`), which the server keeps in the `punchlist_session` cookie (HttpOnly, SameSite=Strict, Secure behind https); every API call from the app uses the cookie alone. The list, the board and the issue page record a `pl:render` performance measure for each render. The list and the board filter by text and assignee (kept in the page) and by project, milestone, labels and statuses (kept in the URL, `/?layout=board&project=<id>&milestone=<id>&label=idea&label=ui&status=todo`, `none` for an issue with none, a list as the key repeated, so a link or a reload keeps them); an issue shows when it matches every filter, has every chosen label and is in one of the chosen statuses. Chosen statuses replace `hide Done and Canceled` and pick the board's columns. `Clear filters` clears them all.
- `pnpm db:prepare`: after changing a query or a migration, migrate the dev database and regenerate `.sqlx/`. Needs `sqlx-cli` (`cargo install sqlx-cli --no-default-features --features postgres,rustls`).
- `punchlist-server bootstrap --person <name>` creates a workspace, its repository and one person, and prints a `pl` config with the person's token.
- `punchlist-server openapi` prints the OpenAPI document as JSON, with no database or environment; `pnpm gen:api` reads it. `punchlist-server serve --web-dir <dir>` (`PUNCHLIST_WEB_DIR`, default `web/dist`) serves the web app's build at `/`, and its `index.html` for any path outside `/api/`; without an `index.html` there it logs one line and serves the API alone.
- What the web app reads (ADR 0006): `GET /api/issues` answers each issue as a row: the issue (with `assignee`, a person or agent, and `labels`, `parent`, an issue id, and `project` and `milestone`, each `{id, name}`), its `run` (`idle`, `queued`, `running`, or `failed` when the latest run in its status failed), its highest-numbered pull request and the gates of its next gated transition (`passed`, `total`, `first_failed`), with the `last_event_seq` of the same snapshot. `GET /api/workspaces/{id}/events?after=<seq>` (the token's workspace, else 404) streams every later event as Server-Sent Events: `id` is the sequence number, `event: issue`, and the data the event with its issue's current row; `Last-Event-ID` replaces `after` on a reconnect. `POST /api/issues` (201) and `PATCH /api/issues/{id}` (`title`, `body`, `labels`, `assignee`, `parent`, `project`, `milestone`, with `null` clearing the last four and unassigning) answer the row and the sequence number of the event they wrote. An edit writes one `edited` event naming the fields that changed, or nothing, and is refused in a status the workflow locks to the caller's role. Creation writes a `created` event. An older `pl` cannot read a timeline with those two kinds, so upgrade `pl` with the server. Four more kinds say only that an issue's row changed, so the open app shows it without a reload: `run` (a claim, a runner finishing an attempt, a lapsed lease; by the runner), `proof` (an upload; by the uploader), `pull_request` (GitHub evidence recorded for the issue's pull requests by a delivery or a read of GitHub; by the workspace's `GitHub` actor) and `workflow` (a load that activates a different version, one per issue in the workspace, which can change every row's gates and status names; by the same actor). The stream carries them and an issue's timeline (`GET /api/issues/{id}/events`, so `pl issue show` and `get_issue`) leaves them out, so they need no upgrade order. GitHub evidence is recorded without the workspace's lock, so its writers add a row to `pull_request_change` instead, and `serve` turns those into one `pull_request` event per issue every 250 ms (`write_pull_request_events`; tests call it themselves).
- Search (PRD R19, ADR 0011): `GET /api/search?q=<text>&limit=<n>` (people only, else 403) answers `SearchResults { hits, more }`: the caller's workspace's issues whose id, title, body or any comment contains `q`, one literal phrase (trimmed, whitespace runs made one space; `\`, `%` and `_` match themselves) in any case, through `ILIKE` on the `pg_trgm` GIN indexes on `issue (id)`, `issue (title)`, `issue (body)` and `comment (body)`. Under 3 or over 200 characters answers 422 (`search needs at least 3 characters`). `limit` defaults to 50, at most 100; `more` says there were more. Hits in the id or title (`in_title`) come first, then the rest, each newest issue first. A hit's `snippet` is the body's match, else the newest matching comment's (`field`, `before`, `hit` as written, `after`, and the comment event's `comment_seq`): up to 40 characters before and 80 after, `…` where cut, whitespace runs and control characters made one space. The list's filter sends it 150 ms after the last keystroke from 3 characters (`useSearch`), shows the hits' rows (still under every other filter; a hit not in the cached list is ignored) with the snippet on one line under the title (`[data-snippet]`, the match in `mark`), and `Enter` on a comment hit opens `/issues/<id>#seq-<n>`, which scrolls that timeline entry (`li#seq-<n>`, any entry) into view and marks it `data-target`. `Esc` in the filter leaves it with its text. `pl search <query> [--limit <n>]` prints `PL-12  <title>` and under it `    body: <before>[<hit>]<after>` or `    comment: …`, `No matches.`, `… more matches; narrow the query`, and exits 1 with the server's message for a refused query.
- Projects and milestones (PRD R17): `pl project create <name>` (`POST /api/projects`), `pl milestone create <name> --project <project> [--pass-when <text>]` (`POST /api/projects/{id}/milestones`) and `pl project list` (`GET /api/projects`: each project, oldest first, with its milestones and their `pass_when`). A name is 1 to 100 characters, unique in the workspace for a project and in the project for a milestone. The app picks them and does not create them. `pl issue create` takes `--body <text>` or `--body-file <path>` (`-` for stdin), as `pl issue edit` does. `pl issue edit <id>` sets `--title <t>`, `--body <text>` or `--body-file <path>` (`-` for stdin, read byte for byte), the labels with `--label <name>` (repeated; replaces them all) or clears them with `--no-labels`, and sets `--parent <id>`, `--project <name>` and `--milestone <name>` (looked up in `--project`, else in the issue's project) and clears them with `--no-parent`, `--no-project` and `--no-milestone`, all in one `PATCH`; `pl issue show` prints the labels, parent, project and milestone that are set. `PATCH /api/issues/{id}` refuses (422) a parent outside the workspace, the issue itself, or an issue under it (`PL-3 is under PL-1 (PL-1 → PL-2 → PL-3), so it cannot be PL-1's parent`); a project or milestone outside the workspace; and a milestone outside the project the issue has after the edit. A new project clears the milestone unless the same request sets one. Edits hold the workspace lock, so two of them cannot make a cycle. An older server ignores the three fields, so upgrade the server before `pl`.
- Linear import (PRD R18): `with-env pl import linear --team KAT --project Punchlist --workspace <id>` reads the project, with its issues from every team that shares it, from Linear's GraphQL API with the personal key in `LINEAR_API_KEY` (sent as `Authorization: <key>`, never to the server and never stored; `LINEAR_API_URL` replaces the endpoint, for tests), posts the snapshot to `POST /api/workspaces/{id}/imports/linear` (the token's workspace, people only, else 404/403; 202 with the run; body limit 64 MB), and polls `GET /api/workspaces/{id}/imports/{run}` until the `linear_import` job is `done` or `failed`, then prints the created and updated counts per record type, the notes and the elapsed time; it exits 1 on failure. Each issue's Linear state maps to a status by the `[import.linear.states]` table in `workflow.toml` (`"QA" = "agent_review"`), else the status whose key or name is the state's name (any case), else by type: backlog → backlog, unstarted → todo, started → in_progress, completed → done, canceled and duplicate → canceled; triage and anything else map nowhere. Any unmapped state answers 422 naming each, as does an issue or comment id the snapshot repeats, and nothing is queued; a state that stops mapping before the job runs fails the job at once (`jobs::Permanent`), not after 10 retries. The job writes everything in one transaction under the workspace lock, keyed by Linear id (`linear_id` on `issue`, `comment`, `project`, `milestone`, `actor`): the project and its milestones (adopting a same-named one not imported yet; a milestone's description is its `pass_when`), each Linear user on first sight as a person with no token, and one `Imported agent` (role `agent`, kind `imported`, no token, owned by the importer) for comments whose last line is `(agent)` or that have no user. New issues are numbered in Linear `createdAt` order with Linear's creation time, creator, status (set directly, no transition), labels, milestone and `linear_identifier`/`linear_url` (`pl issue show` prints `Linear: KAT-12  <url>`), each with a `created` event; parents are linked once all exist. A rerun updates an issue only when Linear's `updatedAt` is newer than the stored `linear_updated_at`: one `edited` event naming the fields (title, body, labels, parent, project, milestone) and, for a new state, a `transition` row and event by the importer, ending a waiting dispatch as any move does; it never dispatches. An issue moved in Punchlist since an import last set its status (a `transition` event after the one in `issue.linear_status_seq`, the importer's own moves included) keeps its status, and the notes name it with Punchlist's status and Linear's state. New comments are added with Linear's time and a `comment` event; edited Linear comments are not updated. Notes report parents outside the project, skipped empty comments, and issues no longer in Linear's project (left in place). `pl import status [--workspace <id>]` (`GET /api/workspaces/{id}/imports`) prints the totals of rows with a Linear id and the last run's state, time, report or error. The report is kept in `job.result`.
- The browser signs in with `POST /api/session` and a person's token (any other token is 401), which sets the cookie `punchlist_session` (`HttpOnly; SameSite=Strict; Path=/`, and `Secure` over https); `GET /api/session` says who is signed in and `DELETE /api/session` clears it. A request without an `Authorization` header is authenticated by that cookie, for people only. `SameSite=Strict` is the defence against cross-site requests.
- The Pull requests page, `/pull-requests` (the approved Page variant, `prototypes/pull-requests/`, `?variant=page`), lists the workspace repository's open and draft pull requests from `GET /api/pull-requests` (people only, 403 to an agent; reads no GitHub; each with its issue as `{id, title, status, status_name}`, `url` only when plain, and `waits_on_merge`: open, not a draft, and its issue's status has an `on = "pr_merged"` transition), in the sections `waits-on-merge`, `in-review`, `draft` and `names-no-issue` (`web/src/model/pull-requests.ts`). `AppHeader` (`web/src/components/app-header.tsx`) on the list, the board and this page links `Issues` and `Pull requests` with the open count, which the list reads only after `GET /api/issues` has succeeded. Keys: `g` then `p` within a second opens the page from the list, the board and the page itself (not from a field, and not on the issue page, where `g` is the gates); `Enter` on a row opens its issue, or the pull request on GitHub when it names no issue; `Esc` goes back to the list. The stream reads the pull requests again on `pull_request`, `transition` and `workflow` events; an event is per issue, so a pull request that names no issue shows its change at the next event or on reload. `punchlist-client` has `pull_requests()`.
- `pl` reads `server_url` and `token` from `~/.config/punchlist/config.toml`, or from the file in `PUNCHLIST_CONFIG`.
- The issue page, `/issues/<id>` (`Enter` on the list's selected row; clicking the selected row still opens the sheet), is the approved Sidebar prototype (`prototypes/issue-page/`): spec (the body, with `- [ ]` lines as acceptance criteria), pull request with its checks table (`#checks`), proof with an upload control, and activity (All, Comments, Transitions, and a composer) in the main column; status and moves, gates (each linked to its evidence), runs and properties in a rail that stacks under the header below 900 px. Keys: `g` gates, `t` activity, `c` composer, `Esc` back to the list. It reads only issue routes, plus for a person the list and the event stream, which invalidates `['issue', id]` on each event for that issue; a running attempt's log is re-read every second (`GET /api/runs/{id}/log`, people only), each line shown as a summary (`logView`: Claude Code's assistant text, tool and target, result; Codex's items) with its raw line a click away. `GET /api/issues/{id}/transitions` lists each transition from the issue's status that no `on` event makes (`Workflow::requestable`), with the caller's verdict from the same `judge_move` a `POST` runs over the recorded evidence, without the GitHub read: `allowed`, `blocked` (the first failing gate's result) or `refused` (`code` and `message`, such as `locked`), and `viewer_locked` when the status locks the caller's role out. A `blocked` move still sends its request, which reads GitHub first and may pass. The page hides a `role_not_allowed` move unless it is the next gated move and a gate fails, so a person sees the agent's blocked Agent Review → Human Review move, disabled. The pull request's title links only to a plain `https://github.com/` URL, and an upload takes its content type from the file's extension (`PROOF_TYPES`). An issue's pull requests (`GET /api/issues/{id}/pull-requests`) carry `check_runs`, the newest of each name on the head commit. Each run and attempt carries `model`: `pl runner start` registers `--model` and `--codex-model` as `models` by agent key, and a claim copies its agent's onto the attempt (none: the agent's own default). Each also carries `reported_model`, the model the agent said it runs on, which the server reads from the first log line that names one (Claude Code's `system`/`init` line or a session assistant message, Codex's `thread/started`; `reported_model` in `runs.rs`), with a `run` event; the run card's second line and `pl run list` show it, with `agent default` or `pinned <model>` beside it, and `waiting for the agent` before it reports.
- A browser whose requests carry a standalone agent's `Authorization: Bearer` header (no cookie: sign-in stays people-only) shows the issue page as that agent: `GET /api/session` answers a standalone agent's token, and the page skips the list, the stream, run logs and proof files. In a status locked to agents it shows the notice and disables the moves, the composer and the upload.
- `pl runner start` registers a runner with that person's token and gets the runner's own token back, held in memory only. The runner's identity is its name: a name the same person already registered in the workspace re-adopts that runner (same id and actor, the new `--agents`) with a new token, and the old token stops working. A runner whose heartbeat gets 401 was re-adopted by another `pl runner start`: it stops every agent and exits, and a claim it was waiting on gets 401 too. On start it first kills every process an earlier process of the runner left, lease lapsed or not (every agent process carries `PUNCHLIST_RUNNER=<runner id>`, found through `/proc`, so Linux only), since an agent leads its own process group and outlives a `kill -9` of the runner; then it reads the attempts it still holds (`GET /api/runners/{id}/leases`), and a Claude Code one whose worktree is still on its branch is resumed (`POST /api/runs/{id}/resume`, `claude --resume <session>` in that worktree, logging on from the next line the server has); any other, Codex included, is reported lost (`runner restarted`). When an attempt ends, however it ends, the runner sends SIGTERM, then SIGKILL after 10 s, to every process carrying `PUNCHLIST_ATTEMPT=<run id>-<attempt>` (set beside `PUNCHLIST_RUNNER`, so a `setsid pnpm dev` a live check left keeps it) and removes the containers labeled `punchlist.attempt=<run id>-<attempt>` (the compose file's `db` takes the label from the variable, so verify-punchlist's `up`, `pnpm dev` and `pnpm check` set it; `scripts/dogfood.sh` clears it), before it reports the outcome, and logs how many of each. A fresh attempt runs `claude --session-id <session>`. It needs `git`, `gh`, and on `PATH` the agents it runs: `claude`, and `codex` (logged in) for Codex. A run acts on GitHub as the workspace's GitHub App, so the runner needs no `gh` login: each claim (and resume) carries an installation token the server mints for the workspace's repository alone (`POST /app/installations/{id}/access_tokens`, `repositories: [name]`) and the App's bot (`<slug>[bot]`, `<user id>+<slug>[bot]@users.noreply.github.com`). The runner writes the token under `<state dir>/github/<run id>/` (removed when the attempt ends): `gh/hosts.yml` (gh's multi-account layout, with `gh/config.yml` at `version: "1"`, since gh would otherwise migrate it by asking `GET /user`, which an installation token cannot), which the agent's `gh` reads through `GH_CONFIG_DIR`, and `token`, which git's credential helper hands out as `x-access-token` for the runner's clone and fetches and the agent's pushes. The agent gets no `GH_TOKEN`, `GITHUB_TOKEN`, `SSH_AUTH_SOCK`, `GIT_ASKPASS` or global or system git config, and its commits are authored and committed by the bot. Ten minutes before the token expires (halfway, for one that lasts under 20 minutes) the runner asks for the next (`POST /api/runs/{id}/github-token`, its running attempt only, else 409 `stale_attempt`; 503 `github_token_unavailable` without App credentials or when GitHub refuses) and rewrites both files, which a running `gh` and git read on their next call; a refresh that fails is asked again every 30 s. The token is not in `GH_TOKEN` because a running agent's environment cannot change. The App needs Contents and Pull requests: Read and write; a claim whose installation lacks either carries `github_error` naming what it grants, and the runner fails the attempt with it. A server without App credentials sends no token and the run uses the runner's own `gh` and git login, as before. `punchlist-server serve --github-token-lifetime <seconds>` (`PUNCHLIST_GITHUB_TOKEN_LIFETIME`, hidden) is a test setting: each token is reported to expire that soon, so a runner refreshes it within minutes. `--agents claude-code,codex` is what it tells the server it can run (default `claude-code`); before registering it refuses a word outside `AGENT_KINDS` with ``unknown agent kind `x`; the kinds are claude-code, codex, opencode, pi, cursor`` (as `POST /api/runners` does, 422) and a kind it has no adapter for with ``unsupported agent `pi`; this runner can run claude-code and codex``; `--model` is Claude Code's model, `--codex-model` Codex's and `--codex-effort` Codex's reasoning effort (default `medium`). A Codex run gets the person's sign-in (`auth.json`, or `CODEX_ACCESS_TOKEN` in the runner's environment) and nothing else of theirs from their Codex home: the runner gives it a `CODEX_HOME` of its own for the run, with apps, plugins and hooks off and every skill disabled, so its only MCP server is `punchlist`. The worktree is an untrusted project to Codex, so the repository's `.codex/` and `AGENTS.md` are not loaded either: the reviewing run takes no instructions from the tree it reviews. With `--codex-model` unset the run uses Codex's built-in default model, and the person's `model_provider`, base URL, proxy and CA settings in `config.toml` do not apply; the runner's environment (`OPENAI_BASE_URL`, `OPENAI_API_KEY`, `CODEX_CA_CERTIFICATE`, `CODEX_ACCESS_TOKEN`) still does. The runner's state goes under `--state-dir` (default `~/.local/share/punchlist/runner`; the `[runner]` table's `state_dir`): its clones (`repos/<owner>/<name>`), worktrees (`worktrees/<owner>/<name>/<issue>`), MCP configs (`mcp/`), run credentials (`github/`) and Codex homes (`codex-home/`). `--worktree-root` (and the table's `worktree_root`) is the old name, hidden, kept for one release; the flag prints `--worktree-root is deprecated; use --state-dir`. With neither set, a runner that finds the old default `~/.local/share/punchlist/worktrees` and no `~/.local/share/punchlist/runner` moves it there with one `rename` (one filesystem), then runs `git worktree repair` in each clone and moves each worktree's Claude Code sessions (`~/.claude/projects/<path>`, or under `CLAUDE_CONFIG_DIR`) to the new path, so its attempts still resume.
- `pl runner start --agent-user <user>` runs the agents as that OS user, so they cannot read the person's files (the Punchlist config with the person's token): it registers the runner with the person's token, then `exec`s `sudo -n -i -u <user> pl runner start --handoff` with the server URL, the runner's id and token and the merged `[runner]` settings as JSON on stdin; that runner reads no config, registers nothing, and resolves `~`, `claude`, `codex` and `pl` in the user's login environment, so its state directory is in the user's home. It needs a sudo rule that lets the person run commands as the user without a password, and `pl` on the user's `PATH`. Without `--agent-user` the runner logs `agents run as <user> and can read this user's files, including the Punchlist config at <path>` first. An agent's environment holds no `PUNCHLIST_*` variable but the ones the runner sets (`agent_env`).
- `pl actor create --agent --kind <kind> [--name <name>] [--model <m>] [--owner <person>]` (`POST /api/actors`, a person's token) mints an agent actor of a kind in `AGENT_KINDS` (`claude-code`, `codex`, `opencode`, `pi`, `cursor`), named `--name` (1 to 100 characters) or after its kind (`Claude Code`), owned by the named person in the workspace or by you, and prints its token once. That standalone agent's token reaches `/api/issues/<id>` and below for its workspace's issues, and `GET`/`POST /api/issues`, `GET /api/workspaces/{id}/events`, `GET /api/projects`, `GET /api/workflow`, `GET /api/actors`, `GET /api/proof/{id}` and `GET /api/session`, each for its own workspace, under the same locks and `by` rules as a run's agent, so it files, lists, edits and watches issues as itself but cannot make a person's move. Anything else (sessions, runners and leases, minting actors, creating projects and milestones, imports) answers 403 `an agent acts only on the workspace's issues`. The orchestrator works as one (`docs/dogfood.md`); a run's agent (kind from the dispatch, owner the person who registered the runner) still reaches only its run's issue while the run runs. `pl actor list` (`GET /api/actors`) prints the workspace's people, agents and runners. Any token on another workspace's issue gets 403, and the server logs `workspace mismatch` with both workspace ids. `pl issue show` marks an agent `name (agent, <kind>)`. No runner claims an issue in a status the workflow locks to agents or runners, even with a dispatch waiting there.
- A transition into a status with a `dispatch.status` rule writes one `dispatch` row. A runner that can run its agent claims it once the issue's running run has ended, and gets the issue's branch, so it reuses the worktree, and the prompt of the workflow version the row was queued under. Claims go in issue order, started issues and waiting dispatches together. An attempt is lost when its runner lost it before the agent finished: the runner stopped or restarted (it finishes the attempt `failed` with `lost`), or its lease expired. A run whose first attempt was lost stays running (unless it is from before runs stored their prompt: it ends) and the next claim of a runner that can run its agent gets attempt 2 of the same run, with the same branch and prompt, a new agent session and a new agent token (the lost attempt's token stops working); a move of the issue meanwhile fails the run. A run that ends otherwise (finished, failed, its second attempt lost) with its issue still in the status that dispatched it gets one more run of the same agent, up to 3 runs per entry into the status; after the third, `pl issue show` prints `waiting on a person: 3 runs in <status> ended without moving it`. This covers In Progress too. The workflow's `[dispatch] max_concurrent` caps the workspace's running attempts (`attempt.state = 'running'`, of any runner): a claim at the cap answers as one with nothing to claim (204 after its wait), moves nothing and writes no run, and a claim waiting at the cap retries any issue when a run ends, so a `finish` lets it through at once; a lease that lapses frees its slot only when the sweep fails the attempt, and a run waiting for its next attempt holds none. `POST /api/runs/{id}/resume` is not a claim and is never refused by it. The cap is read from the active workflow at each claim; lowering it stops no running attempt. With no key the only limit is each runner's `--max-concurrent`. A dispatch rule with `serial = true` (a bool, default false; any other value is refused at load naming `dispatch.status.<status>.serial`) gives out one run in its status at a time: while a run in that status is running in the workspace (one repository), a new run there waits, a run waiting for its next attempt included, and other statuses are claimed as before. A finish wakes the runners for the next dispatch waiting in the run's status. Punchlist's own workflow sets it on Merging, so each merge lands on the `main` the previous one left. A run whose agent called `wait_for_person(reason)` gets no next run: the tool sends `POST /api/runs/{id}/waiting` (the run's own agent, else 403; 409 `stale_attempt` once the run has ended, the one route an ended run's agent token reaches; `reason` 1 to 500 characters; refused in a status locked to agents, as comments are), which stores `run.waiting_reason` and posts the reason as the agent's comment, and the issue read (`GET /api/issues/{id}`, so `pl issue show`, `get_issue` and the issue page) answers `waiting_on_person` as `<agent> is waiting on a person: <reason>`, ahead of the 3-runs text, until a move starts a new entry. `pl mcp` gets the run's id from `PUNCHLIST_RUN`, which the runner sets. A heartbeat answers which held attempts are stale, and the runner stops their agents. `pl run list <issue>` prints each run and under it each attempt with its runner, outcome and reason. Under the PRD's workflow, Agent Review dispatches Codex (`codex app-server`, the adapter in `crates/punchlist-runner/src/codex.rs`), and Merging dispatches Claude Code, which brings the pull request up to date, resolving conflicts, and squash-merges it (`.punchlist/prompts/merging.md`); the merge moves the issue to Done, and a pull request it cannot merge (a failed check, a draft, a conflict it cannot resolve) ends the run with `wait_for_person`.
- GitHub events arrive at `POST /api/github/webhook`, verified with the GitHub App's webhook secret in `GITHUB_WEBHOOK_SECRET` (or `punchlist-server --github-webhook-secret`; it is a secret, so start the server under `with-env`). `pl issue show` lists an issue's pull requests; `pl pr unlinked` lists the ones that name no issue. An issue that enters a status with an `on = "pr_merged"` transition (Merging) when its highest-numbered pull request is recorded merged and none is open takes that transition at once, in the same transaction, as the merge's webhook would have (`catch_up_merge` in `github.rs`, the same gates, actor `GitHub`); `serve` does it at start for every issue already waiting there. `pr_closed_unmerged` is not caught up.
- The server reads `.punchlist/` from the workspace repository's default branch as the GitHub App, with `GITHUB_APP_ID` and `GITHUB_APP_PRIVATE_KEY` (a secret; one-line PEM is fine). The App needs Contents read, Pull requests read (the pull request and review-thread reads), Checks read (GitHub App settings, Permissions, Repository, Checks: Read-only, accepted on the installation before this is deployed: without it the read answers 403 and every gated request on an open pull request is refused; `GET /repos/{owner}/{repo}/commits/{sha}/check-runs`), the Push event and, only for a workspace whose workflow requires a GitHub Actions check in `[gate.ci_green]`, Actions read (Actions: Read-only, accepted the same way; without it that workspace's gated requests on a pull request with a run of a required name are refused, 403; `GET /repos/{owner}/{repo}/actions/runs?head_sha=` and each run's `/jobs`). As the App the server reads a pull request's current state (REST) when a delivery would close it without a merge, and before a gated request its review threads (GraphQL `reviewThreads`) and the check runs on its head commit (REST), with the workflow jobs behind the runs of the GitHub Actions checks the workflow requires; a failed read refuses the request. Without App credentials the server reads nothing and records payloads in the order they arrive. `bootstrap` queues the first load; a push that changes `.punchlist/` queues the next, and `serve` with App credentials queues one per workspace at start, since GitHub does not redeliver a push the stopped server missed. A load of the active version's file changes nothing, its commit included. A file that drops a status an issue is in is refused too, as is a dispatch rule whose `agent` is not one of `AGENT_KINDS` (``line 61, `dispatch.status.agent_review.agent`: unknown agent kind `opncode`; the kinds are claude-code, codex, opencode, pi, cursor``); a kind no runner can run yet, such as `opencode`, loads. `pl workflow show` prints the active version, with an `Invalid` line when a push of that stored version would be refused today (it stays in force until a valid file is pushed; the server warns once at start), and a `Refused` line with the commit and reason when the last pushed file was refused; `GET /api/workflow/schema.json` is the JSON Schema.
- `[gate.ci_green]` in the workflow file, with `required = ["test", { name = "deploy", app = "vercel" }]`, names the checks `ci_green` needs a successful run of on the head commit, each from its GitHub App's slug (a bare name is `github-actions`); `check_run.app` records the app. A required `github-actions` check counts only when a runner ran its job (`check_run.workflow_path` is that job's workflow file; a check run created through the API has none) and that file at the head commit is the default branch's (`workflow_sha` equals `workflow_default_sha`); nothing waives it, so the branch takes the default branch's file, and a real workflow change is merged there by a person first. It also counts only when every pull request from its run's head branch in the workspace's repository, open or closed, has only been into the default branch, earlier bases included (`check_run.workflow_other_bases` is empty): a pull request's run takes its workflow file from its base, and GitHub does not say which pull request a run was for. The read asks GraphQL `pullRequests(headRefName:)`, with each pull request's `BaseRefChangedEvent`s, once per head branch. A fork's run or a branch with no pull request (NULL) never counts, and a branch that has ever had a pull request into another base needs replacing with a new branch. A job counts for a check run only when its id, name, conclusion and commit are the check run's. Only a gated request's read of GitHub records these, so a server without App credentials satisfies no required GitHub Actions check. An older server cannot load a file with that table, so revert the file before rolling back past it. `pl issue transition <id> <status>` requests a transition and prints any failed gate; `pl issue comment <id> --body` comments. `pl issue show` prints the checklist for the issue's next gated transition (`GET /api/issues/{id}/gates`), over the evidence recorded then, and ends it `n of m gates pass`. `ci_green` reads the newest check run of each name in each check suite on the pull request's head commit and fails when none has reported; `mergeable` needs GitHub's merge state `clean` or `has_hooks`; `no_open_threads` names each unresolved review thread by path and line; `proof_attached` needs at least one proof record from the issue's current attempt, and its reason names the attempt. A gate result keeps Punchlist's sentence (`reason`) apart from the names GitHub's users wrote (`outside`: check names, thread files); `GateResult::text()` joins them for people and for the stored rows, and `request_transition` prints the sentence plainly (`Refused (gate_failed): gate <gate> failed: <sentence>`, never the API's `message`) and the names inside a fence of its own, each line behind `> `. A reason names at most five checks or threads; `outside_more` counts the rest. An older server sends the joined string as `reason`, which `pl mcp` cannot tell apart, so upgrade the server before `pl` and `pl mcp` on the runners; until then a refusal reaches the agent unfenced, as before. Each claim creates an agent actor whose token works only while its run runs; the runner gives it to `pl mcp`, which Claude Code gets as the `punchlist` MCP server (`get_issue`, `edit_issue`, `comment`, `attach_proof`, `request_transition`, `wait_for_person`). `edit_issue(title?, body?)` sends `PATCH /api/issues/{id}` for the run's issue with the run's token, so the `edited` event is the agent's; it takes no issue id and sets nothing else, and a refusal (`locked`) answers as the other tools do. `get_issue` first has the server read the issue's pull requests and their review threads from GitHub (`POST /api/issues/{id}/pull-requests/refresh`, the only route that returns thread text), since a new thread sends no webhook, and prints each unresolved thread of an open pull request: its id outside the fence, and inside it the file, authors and comments, each line of them behind `> `. The issue's title, body, comments and refused transitions' reasons are behind `> ` too, so inside the fence only Punchlist writes a line without it; a comment's actor name is on a quoted `Author:` line, and a pull request's URL is printed only when it is a plain `https://github.com/` path. The runner's prompt quotes the title and body the same way, and refuses the run (`Failed`) when the branch or the repository's owner, name or default branch is not a plain name (letters, digits, `. _ / -`); `request_transition` does not echo an unknown status. A thread's last 10 comments are recorded, each cut at 2000 characters; at most 30 threads and 60 kB of them are printed; the output says when any of these cut something, and when GitHub could not be read and the threads are the recorded ones. The Agent Review prompt has the agent read reviewers' text only there. A `pl` with this `get_issue` needs a server with that route, so upgrade the server before the runners.
- Proof is a file attached to an issue to show its work. `pl proof attach <id> <path> --title <t> [--kind image|video|report]` uploads one (`POST /api/issues/{id}/proof`, multipart `title`, `kind`, `file`), and the MCP tool `attach_proof(path, title, kind)` does the same as the run's agent; `pl proof list <id>` (`GET /api/issues/{id}/proof`) and `pl issue show` list each with kind, title, size and uploader. A file's type comes from its extension, from one table in `punchlist-api` (`PROOF_TYPES`): png, jpg, jpeg, gif, webp (image); mp4, webm, mov (video); txt, log, md, xml, pdf (report). No HTML, SVG or JSON. The server accepts only those content types and stores the bytes under `punchlist-server serve --proof-dir` (`PUNCHLIST_PROOF_DIR`, default `~/.local/share/punchlist/proof`), up to `--proof-max-bytes` (`PUNCHLIST_PROOF_MAX_BYTES`, default 104857600; over it answers 413). `GET /api/proof/{id}` serves a file with its content type, `nosniff` and `Content-Security-Policy: sandbox`, to people, runners and standalone agents of its workspace (a run's agent gets 403). Each record holds the issue's attempt when it was uploaded: how many times the issue has moved from Start to In Progress, 0 before the first (not the `attempt` table's per-run number): the attempt when the upload started, and an upload during which the issue moved to a new attempt is refused (409 `stale_attempt`). The issue and its lock are checked before the file is read, and again when it is recorded. An agent cannot attach proof in a status the workflow locks to agents, as for comments.
- Secrets never go in a `.env` file. Commands that need one run under `with-env` (the Punchlist 1Password Environment).

Make a live call only inside a named live check.

## Rules for the code

- The workflow lives in `.punchlist/workflow.toml`, and prompts live in `.punchlist/prompts/` (ADR 0001). Never put workflow rules in a prompt.
- A gate is a pure function in `punchlist-core` over recorded evidence. An agent's claim that a gate passed is never evidence.
- The server checks roles, locks and gates for a transition in one transaction, and records the actor, the workflow version and each gate result.
- Parse external data where it enters: workflow files, GitHub webhooks, Linear imports, agent requests. Trust typed data inside.
- Text from outside the team reaches an agent only inside a fence that the text cannot close.
- Runs are idempotent per issue and attempt. A claim is a lease, and a runner restart never loses or duplicates a run.
